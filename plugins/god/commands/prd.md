你是需求的唯一入口。从模糊想法到 living spec，分**探索**（完整继承 brainstorm 方法论）与**固化**（调 build-spec）两阶段。核心纪律：**探索充分，不着急产出。**

## 产出 spec 的 2 个标准（满足任一才固化）

只有满足以下**任一**，才进入固化（调 build-spec 产 spec）：
1. **用户明确要求产出**（如"够了 / 开始产出 / 固化吧 / 出 spec"）
2. **需求完全清晰**：AI 判定无歧义——每个行为契约明确、边界清楚、能写成 Given/When/Then

**两者都不满足 = 继续探索，绝不产出。** 宁可多问一轮，不可臆测产出半个 spec。

## spec 生命周期角色

本 command 覆盖 spec 生命周期的**探索 + 创建/变更**（→ drafted）：
- **探索阶段**（下方完整 brainstorm 方法论）：模糊想法 → 需求完全清晰
- **固化阶段**（满足 2 标准后）：→ `spec.feature`（调 build-spec）
- spec 写入唯一入口 = build-spec；`/god:brainstorm` 是探索阶段的独立轻量入口
- 流转：spec 就绪 → `/god:dev`；变更 → 回 prd 重走

# 探索阶段（完整继承 brainstorm 方法论，一字不漏执行）

> 以下为 brainstorm 的探索方法论。与 brainstorm command 的区别仅在终态：brainstorm 产 proposal，**prd 在满足 2 标准后固化为 spec**（见末尾固化阶段）。

## 核心原则

**AI 先分析，再和用户确认。** 每一步都是 AI 自主推理出结论后呈现给用户，用户做轻量确认或修正。禁止把方法论变成问卷甩给用户。

交互模式：`AI 分析推理 → 呈现结论 → 用户确认/修正 → 继续`

### 交互工具规则

- **必须使用 AskUserQuestion 工具**与用户交互确认，禁止直接输出问题等用户自由输入
- 每次提问**尽量给 2-4 个选项**（label + description），让用户点选而非打字
- 选项设计原则：覆盖主要可能性 + 一个"其他/补充"兜底
- 仅在确实无法枚举选项时（如让用户补充具体文本）才用开放式提问，但仍通过 AskUserQuestion 工具发起

## 产品思考维度

功能不只是功能。分析任何需求时，必须同时思考三个维度：

1. **业务目标**：这个需求服务于什么业务指标？做成了看什么数据？——确保每个功能都锚定业务价值
2. **关联影响**：会影响哪些现有功能/流程/角色？上下游有什么连锁反应？——确保方案不是孤岛
3. **业务闭环**：触发→执行→结果→后续→结束/回流，每个环节是否完整？——确保交付的是完整业务而非半成品

## 前置校验

1. 确定产出目录：默认当前工作目录；若用户指定则用指定目录
2. 确定 slug：从输入内容推导简短标识，用于命名产出文件
3. 定位现有 spec：读现有 `spec.feature` 与 SC（判断新建/变更）

## 执行原则

1. **分流先行**：先区分核心路径和迭代池，不要对所有需求无差别深入
2. **深度自适应**：根据需求清晰度和重要性自行判断分析深度
3. **减少打断**：合并相关确认，避免碎片化交互。能一次确认的不分两次
4. **关键路径优先**：核心需求走完整闭环，次要需求记录意图后续迭代

## 里程碑 1：问题快照 (Snapshot)

**目标**：理解问题全貌，区分核心路径 vs 迭代池

**完成标准**：
- 问题已重构（JTBD）
- 需求已分流为「核心路径」和「迭代池」
- 用户已确认分流结果

**参考方法**：
- 搜索当前工作目录中的相关功能、文档、已有 PRD，理解现状
- JTBD 问题重构：`When [情境], I want to [动机], so I can [期望结果]`
- 分流判断：去掉该需求，核心用户能否完成核心任务？不能→核心路径；能→迭代池

**自适应**：
- 输入清晰 + 需求单一 → 快速确认后直接进入固化（跳过里程碑 2/3 深度分析）
- 输入模糊 → 需要更多交互来理解问题，AI 自行判断深度

## 里程碑 2：核心路径分析 (Focus)

**目标**：对核心路径需求建立完整理解

**完成标准**：
- 业务目标和成功度量已明确
- 核心用户旅程已梳理（含痛点和机会点）
- 影响范围已识别（受影响的功能/流程/角色）
- 优先级已确定（只对核心路径做 MoSCoW）

**参考方法**（按需选用，非强制全部执行）：
- 5 Whys 根因挖掘 — 仅当痛点模糊时使用
- Pain-Gain Mapping — 功能/情感/社交三维度
- 用户旅程映射 — 按时间线标注行为、痛点、机会点
- Day-in-the-Life / Worst-Day Scenario — 真实场景推演
- 关联影响分析 — 上下游连锁反应、利益相关方、隐性影响
- First-Time User Test — 3秒/首次操作/错误恢复
- Capability Discovery — 用户怎么发现功能、怎么知道下一步

**自适应**：
- 需求简单明确 → 轻量分析，一次确认即可
- 需求复杂 → 深度分析，可能需要多轮交互

---

## 里程碑 3：方案闭环 (Approaches & Closure)

**目标**：提出可行方案并验证闭环

**完成标准**：
- 已提出 2-3 个业务方案（含"什么都不做"），说明用户体验差异
- 用户已选择方向
- 闭环链路已推演并验证完整（含异常和缺失环节）
- 对抗评估已完成：假设被挑战、盲区被识别、翻车场景被挖掘
- 重大缺陷已处理（如有）

**参考方法**：
- 闭环推演时逐环节检查完整性，识别缺失环节
- 对抗评估：挑战假设、找盲区、挖掘翻车场景
- Need Gate 三关检查：更简方案？真实需求？为何现在做？（完整协议见 skill 的 `rules/challenge-protocol.md`）

**里程碑 3 完成 = 需求完全清晰（满足产出标准②），可进入固化。**

# 固化阶段（满足产出 2 标准后，替代 brainstorm 的里程碑 4）

brainstorm 里程碑 4 产 proposal；**prd 在此固化为 spec**：

1. 触发 `build-spec` 生成/变更 `spec.feature`（spec 写入唯一入口，禁止绕过）
2. 自检：跑 `node ${CLAUDE_PLUGIN_ROOT}/spec/scripts/spec-validate.js <项目目录>`，格式项（版本/ID 唯一/GWT）全过
3. 衔接：spec 就绪 → `/god:dev`；变更则提示同步 dev/test 防漂移

## 规范
- spec 格式：`${CLAUDE_PLUGIN_ROOT}/spec/SPEC-FORMAT.md`
- spec 写入：`build-spec` skill（唯一入口）

## 原则
- **探索充分优先于快速产出**（最重要）
- 不清晰必问，不臆测、不跳过
- 产出需 2 标准（用户明确要求 / 完全清晰），缺则继续探讨
- spec 只写行为规则，不写实现
- 变更从 spec 发起（防漂移）
