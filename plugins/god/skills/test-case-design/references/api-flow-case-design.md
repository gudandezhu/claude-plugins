# API 业务流程测试案例设计规范

产出：`{flowCasesOutputPath}`（由主会话展开为绝对路径后传入）
消费方：run-test → run-test

## 流程案例的定位

单接口测试太碎（只验证参数校验），E2E 太重（含 UI 交互），
流程测试填补中间层——验证多接口串联的业务逻辑正确性，真实 API 调用不 Mock。

## 四种流程类型

| 类型 | 说明 | 示例 |
|------|------|------|
| CRUD 完整流程 | 创建→查询→修改→删除 | 新增规则→查询列表→编辑规则→删除规则 |
| 状态流转流程 | 实体在不同状态间流转 | 草稿→提交→审批→生效 |
| 业务联动流程 | 操作 A 影响实体 B | 删除分类→关联规则自动失效 |
| 异常中断流程 | 流程中某步骤失败的恢复 | 审批中→驳回→重新提交 |
| 端到端链路 | 跨多个业务实体的完整业务路径 | 请购单创建→提交→生成采购单→到货 |

## 流程识别方法论（强制执行）

case-designer 在设计流程案例前，必须按以下三步识别完整的业务流程，禁止跳过。

### 第一步：业务实体生命周期分析

从 PRD 和 ac.md 中识别所有业务实体（如：请购单、请购明细、采购单），
为每个核心实体绘制完整生命周期：
- 创建 → 编辑 → 提交 → 审批/驳回 → 生效/作废 → 删除
- 每个状态转换必须对应一个流程案例
- 如果 PRD 中描述了实体的某个操作（如"添加物料"），即使 ac.md 中没有对应的独立 AC 编号，也必须设计流程覆盖

### 第二步：写操作全覆盖

从 AC 的操作类条目（AC-OP-*）提取所有写操作，每个写操作必须出现在至少一个流程中：
- 新增/创建（如：新增请购单、添加请购物料）
- 编辑/修改（如：编辑请购单）
- 删除（如：删除请购单）
- 状态变更（如：提交至采购、撤回、作废）
- 业务联动（如：生成采购单、采购单状态回写）

仅有查询类流程是不合格的——查询只是流程中的验证步骤，不是独立的业务流程。

### 第三步：状态流转路径覆盖

从 AC 的状态枚举（AC-STS-*）提取所有状态值，确保：
- 每个合法的状态转换路径至少被一个流程覆盖（如：待提交→已提交、已提交→已作废）
- 非法的状态转换（如：已作废→编辑）有异常中断案例
- 特殊状态（如：AI识别中）的行为限制有对应验证

### 流程识别产出

完成三步分析后，在案例文档的"流程案例总览"表中体现所有识别出的流程，
确保总览表中包含 CRUD、状态流转、业务联动、异常中断四种类型的流程。

## TC 编号规范

| 类型 | 格式 | 示例 |
|------|------|------|
| 正常流程步骤 | FLOW-{模块}-{流程序号}-S{步骤号} | FLOW-RULE-001-S01 |
| 异常中断 | FLOW-{模块}-{流程序号}-E{异常号} | FLOW-RULE-001-E01 |
| 边界流程 | FLOW-{模块}-{流程序号}-B{边界号} | FLOW-RULE-001-B01 |

## 步骤链 JSON 格式

每个流程案例的 steps 必须是对象数组（Flow Schema 专用格式）：

> **FLOW- 案例双驱动说明**：FLOW- 案例同时驱动 E2E 流程脚本和 API 流程脚本的生成。
> steps 中的字段同时服务两种脚本：
> - "action" → E2E 脚本的 UI 操作
> - "api"+"params" → API 脚本的请求构造
> - "uiExpected" → E2E 脚本的断言依据
> - "apiExpected" → API 脚本的断言依据（HTTP 状态码、关键响应字段、状态变更验证）
>
> 两种断言依据必须分字段，不共用——UI 断言（元素可见/文本匹配）与 API 断言（状态码/JSON 字段）验证方式完全不同。

```json
{
  "id": "FLOW-RULE-001",
  "title": "对账规则完整 CRUD 流程",
  "priority": "P0",
  "type": "flow_happy",
  "flowType": "CRUD 完整流程",
  "writeOps": ["创建规则", "编辑规则", "删除规则"],
  "covers": ["AC-XXX"],
  "preconditions": ["后端服务已启动", "已获取认证 token"],
  "steps": [
    {
      "step": "S01",
      "tc": "FLOW-RULE-001-S01",
      "action": "创建规则",
      "api": "POST /rule/add",
      "params": "ruleName, ruleType",
      "uiExpected": "页面提示\"创建成功\"",
      "apiExpected": "200, {code:0, data:{bizKey: not null}}",
      "dataPass": "bizKey → S02"
    },
    {
      "step": "S02",
      "tc": "FLOW-RULE-001-S02",
      "action": "查询验证",
      "api": "GET /rule/list",
      "params": "keyword=ruleName",
      "uiExpected": "列表包含新建规则",
      "apiExpected": "200, {data:{list: contains(ruleName)}}",
      "dataPass": "—"
    }
  ],
  "cleanup": "afterAll 中通过 DELETE 接口清理 S01 创建的数据",
  "design_method": "流程识别",
  "tags": ["CRUD", "规则"]
}
```

## 覆盖要求

- 每个核心业务模块至少 1 个 CRUD 完整流程
- 如果 PRD 涉及多个业务实体的联动（如请购单→采购单→到货），
  必须设计至少 1 个跨模块端到端链路流程（FLOW-COMPLETE-001），
  覆盖从创建到最终状态的完整业务路径
- 跨模块流程的优先级为 P0
- 每个业务实体的完整生命周期至少 1 个流程覆盖（创建→使用→清理）
- 每个 AC-OP-* 操作至少出现在 1 个流程步骤中（不能只声明覆盖，必须有实际步骤）
- 每个合法的状态转换路径至少被 1 个流程覆盖
- 每个流程至少 1 个异常中断案例（E 编号）
- 流程步骤间的数据传递必须明确标注（如 bizKey → 下一步）
- 禁止只有查询类流程——必须包含写操作流程（创建/编辑/删除/状态变更）

## 造数策略

- 真实 API 调用，不 Mock
- 测试数据名称前缀：`FLOW测试_${Date.now()}`（与单接口的 `API测试_` 区分）
- afterAll 必须清理测试数据

## 覆盖AC 标注（ac.md 存在时）

每个流程案例的 covers 数组填写对应的 AC 编号（如 ["AC-FLOW-01"]）。
ac.md 不存在时 covers 为空数组。

## 禁止事项

- 禁止 Mock 任何接口——流程测试的价值在于验证真实接口串联
- 禁止在 scope 为 frontend 时生成流程测试——流程测试是纯 API 测试
- 禁止与单接口测试使用相同的 TEST_PREFIX——会导致数据清理互相干扰
