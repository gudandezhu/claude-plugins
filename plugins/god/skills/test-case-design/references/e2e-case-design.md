# E2E 测试案例设计规范

产出：`{e2eCasesOutputPath}`（由主会话展开为绝对路径后传入）

## 业务目标牵引

案例设计以 businessObjective（核心业务目标）为首要牵引：
1. 优先覆盖业务目标直接相关的功能点
2. 每个业务目标至少有 1 个 P0 正常流程案例 + 1 个 P0 异常案例
3. 案例描述中标注关联的业务目标

## AC 驱动案例设计（ac.md 存在时）

当 ac.md 存在且包含 AC-/UI- 编号时，案例设计以 AC 为主线：

1. **逐条 AC 设计用例**：每个 AC/UI 编号至少有一条用例覆盖
   - 排除规则定义类（AC-STS-/AC-CALC-/AC-FMT-）：被功能 AC 引用，不是独立测试目标
   - 排除非功能需求类（AC-NF-）：性能/安全需专项测试，不生成 E2E 用例
2. **标注覆盖关系**：每条用例的"覆盖AC"字段填写对应的 AC 编号
3. **GOAL 作为牵引**：GOAL 类（G-N）不直接覆盖，但用例设计应体现 GOAL 的业务价值
4. **PRD 补充**：AC 未覆盖的隐含场景从 PRD 补充，标注"PRD 补充"

ac.md 不存在，或 ac.md 存在但内容中无 AC-/UI- 编号时，此章节跳过，按功能点驱动模式设计。

## 案例格式（强制）

每个案例使用 JSON 格式输出，只写入 .json 文件（不写 .md）。MD 由主会话 json-to-md.js 自动生成。

JSON test_cases 数组中每个条目格式：

```json
{
  "id": "FE-{页面}-001",
  "title": "一句话描述",
  "priority": "P0",
  "type": "happy_path | negative | edge_case | exception",
  "testPath": "首页 > 模块 > 页面",
  "covers": ["AC-XXX"],
  "preconditions": ["前置条件1", "前置条件2"],
  "steps": ["操作步骤1", "操作步骤2"],
  "expected": ["预期结果1", "预期结果2"],
  "design_method": "AC 驱动 | PRD 补充 | 菜单树补充",
  "tags": ["标签"]
}
```

字段说明：
- **id**：`FE-{模块}-001`，异常加 -E01 后缀，边界加 -B01
- **covers**：AC 编号数组，格式 `["AC-001"]`（这是覆盖率检查的唯一数据源）
- **testPath**：从首页到达目标操作位置的完整导航链路
- **type**：happy_path=正常, negative=异常, edge_case=边界, exception=异常场景
- version 和 lastUpdatedBy 在 JSON 文件头部统一声明，每个案例不重复

### 测试路径格式

每个案例必须声明从首页到达目标操作位置的完整导航链路，让测试执行者（人或 AI）无需猜测如何到达目标页面。

#### 数据来源（按优先级）

1. **tree-context.json 的 menuTree**（最佳）：`menuTree.pages[].path` 包含结构化的菜单层级路径。E2E case-designer 必须优先从此提取导航路径。
2. **PRD + UI 原型**（回退）：当 tree-context.json 不可用（status=NO_MATCH）时，从 PRD 中的菜单描述、UI 原型中的导航截图推导。每条路径后标注 `(PRD推导)` 提醒用户核实。
3. **dom-probe-summary.json**（仅 gen-test-script 阶段有，case-designer 阶段不可用）

**格式**：`顶部导航 > 侧边栏菜单 > 子菜单 > Tab/按钮 > 弹窗/抽屉`

**示例**：
```
测试路径: 人事财务 > 银行协同管理 > 账务查询
测试路径: 右上角头像 > 账号设置 > 企业信息 > 银行直联配置 Tab
测试路径: 人事财务 > 银行协同管理 > 支付转账 > + 新增单笔支付按钮 > 新增支付弹窗
测试路径: 人事财务 > 银行协同管理 > 账务查询 > 某笔记录操作列 > 详情按钮 > 详情抽屉
```

**规则**：
- 必须从可识别的起点开始（顶部导航栏、头像菜单等），禁止省略中间层级
- 路径元素用 `>` 分隔，每个元素用 UI 上可见的文本标注
- 如果案例的测试步骤本身就是导航（如菜单显示验证），测试路径写 `首页` 即可
- Tab 用 `Tab名 Tab` 标注，弹窗用 `按钮名 > 弹窗名弹窗` 标注，抽屉同理
- 同一模块下的多个案例如果路径相同，可以复用同一条路径

## 覆盖完整性（强制，覆盖率 ≥ 80%）

必须覆盖以下所有类型：

- 正常流程（Happy Path）：所有主流程的完整操作，每个主流程至少 1 个案例
- 异常流程（E 编号）：每个表单提交至少 1 个异常案例（接口报错、数据不存在等）
- 边界值（B 编号）：每个输入字段至少 1 个边界案例（空值、最大长度、特殊字符）
- 表单验证：每个必填字段至少 1 个空值提交验证案例
- 交互状态：加载中、空状态、分页（如有）

## PRD 驱动的案例设计（强制）

### 从 PRD 功能表提取
- 每个「元素名称」对应至少 1 个正常流程案例
- 每个「异常提醒」对应至少 1 个异常场景案例
- 每个「触发事件」联动描述对应至少 1 个联动测试案例

### 从 UI 原型提取
- 输入框的 min/max/step → 边界值案例
- 下拉框选项列表 → 每个非默认选项至少 1 个案例
- 必填标记 → 空值提交校验案例

### 从 PRD 异常场景表提取
- 每条异常场景对应 1 个 Mock 测试案例
- 重点：保存失败、删除失败、开关切换失败的前端恢复行为

## PRD 不足时 AI 补全

PRD 中未明确的异常场景，AI 可基于业务常识补充，但必须标注"AI 补充"：
```markdown
| 用例ID | ... | 备注 |
| FE-RULE-E03 | ... | ⚠️ AI 补充：PRD 未明确此异常场景 |
```

## 菜单树异常场景补充（tree-context.json 存在时）

从 tree-context.json 的 `menuTree.pages[].interactions[].fail` 提取异常场景：
- 每个 fail 分支对应 1 个异常案例
- 案例的 dataStrategy 声明为 "level-3"（需 Mock 接口）
- dataStrategyNote 填写 Mock 需求：如 "Mock 查询接口返回 500"
- 标注 "菜单树补充" 而非 "AI 补充"（来源可追溯）

示例：
```markdown
| FE-PRQL-E04 | 保存请购单接口超时 | P1 | 异常测试 | 请购单已填写 | 1. 填写请购单信息 2. Mock保存接口延迟 3. 点击保存 | 1. 显示toast"保存超时" 2. 表单不关闭 | 菜单树补充 |
```

## 菜单树页面状态补充（tree-context.json 存在时）

从 tree-context.json 的 `menuTree.pages[].states` 提取交互状态案例：
- `loading`: 1 个加载状态案例（骨架屏 → 数据返回后骨架消失）
- `empty`: 1 个空状态案例（空数据提示 + 新建入口可点击）
- `error`: 1 个错误状态案例（Mock 500 后错误提示 + 重试按钮）

这些案例为交互状态验证，优先级 P1，标注"菜单树补充"。

## testDataMap

**不在案例文档中生成 testDataMap**。testDataMap 由 script-writer 阶段根据案例文档自动提取生成。

## 案例数量合理性

- E2E 案例 < 15 个：⚠️ 可能覆盖不足
- E2E 案例 > 35 个：⚠️ 可能过于细碎，考虑合并
- 建议范围：15-30 个

## 禁止事项

- 禁止包含 CSS 选择器或 DOM 结构描述
- 禁止包含脚本代码片段
- 禁止使用简化格式（只有三列的概要表格）
- 禁止只写正常流程——异常/边界/验证场景是强制要求
