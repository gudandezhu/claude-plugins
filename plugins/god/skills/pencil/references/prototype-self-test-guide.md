# 原型自测指南

## 概述

本指南定义了产品原型自测的详细流程和方法，旨在确保原型的**完整性**、**一致性**和**可操作性**。

**核心目标**：
- 确保原型覆盖所有功能清单中的功能
- 确保原型与PRD文档保持一致
- 确保原型操作流程完整闭环
- 在进入阶段7（需求文档自审）前，发现并修复原型问题

**类比**：如同代码开发中的"单元测试"和"集成测试"，原型自测是产品开发中的"功能测试"。

---

## 自测时机

**触发条件**：
- 阶段6（原型设计）完成后
- 进入阶段7（需求文档自审）前
- 原型文件创建完成后必须执行

**预计耗时**：
- 小型原型（1-3个页面）：30-60分钟
- 中型原型（4-10个页面）：1-2小时
- 大型原型（10+个页面）：2-3小时

## 自测流程

### 第零步：PRD 章节强制映射（⛔ 最高优先级，必须在所有其他步骤之前执行）

**目标**：防止虚假覆盖率汇报，确保原型真正覆盖了 PRD 定义的每一个功能模块

> **⛔ 强制规则**：
> 1. **功能清单总数来源于 PRD 第5章，不允许自行定义**
> 2. **必须逐章映射**，PRD 5.1 ~ 5.N 的每一个章节都必须出现在映射表中
> 3. **不允许跳过任何章节**，即使该章节因设计变更改变了实现方式，也必须标注"设计变更"并说明替代方案
> 4. **覆盖率的分母是 PRD 章节数，不是已实现的页面数**
> 5. 未执行本步骤的自测报告视为无效

#### 0.1 PRD 章节 → 原型页面映射表（⛔ 强制模板）

从 PRD 文档第5章（功能描述）中提取所有章节，逐个映射：

| PRD章节 | 功能名称 | 页面类型 | 原型页面ID | 实现状态 | 备注 |
|---------|---------|---------|-----------|---------|------|
| 5.1 XXX列表 | 列表页 | 列表页 | bZ3bj | ✅ 已实现 | — |
| 5.2 XXX按钮 | 按钮操作 | —（属5.1页面） | bZ3bj | ✅ 已实现 | 操作在列表页内 |
| 5.3 XXX配置 | 新增页面 | 列表页 | — | ❌ 未实现 | **需补做** |
| 5.4 XXX按钮 | 按钮操作 | —（属5.3页面） | — | ❌ 未实现 | 依赖5.3页面 |
| 5.5 XXX表单 | 弹窗表单 | 弹窗 | — | ❌ 未实现 | **需补做** |
| 5.6 XXX日志 | 新增页面 | 列表页 | — | ❌ 未实现 | **需补做** |
| 5.7 关联改动 | — | — | — | ⬜ 不适用 | 非页面功能 |
| **合计** | **__ 个功能章节** | — | — | **__ 个已实现 / __ 个未实现** | — |

**状态说明**：
- ✅ **已实现**：原型中有对应页面/功能，且交互完整
- ⚠️ **设计变更**：PRD 原方案因用户反馈改变了实现方式，必须在备注中说明替代方案
- ❌ **未实现**：原型中完全缺失，必须在备注中标注"**需补做**"
- ⬜ **不适用**：非页面类章节（如关联改动、非功能需求），不计入覆盖率

#### 0.2 设计变更追踪（⛔ 有设计变更时必须填写）

当用户在原型阶段改变了 PRD 的设计方案时（如：弹窗改为完整页面、独立页面改为内嵌组件），必须填写：

| PRD章节 | 原方案 | 变更后方案 | 变更原因 | 变更影响 | 是否仍需补做页面 |
|---------|--------|-----------|---------|---------|----------------|
| 5.3 跳过规则配置 | 独立列表页 | 审批节点表格内嵌开关+条件列 | 用户反馈要求集成 | 5.4按钮操作一并改变 | 否，已替代 |
| 5.5 新增编辑弹窗 | 弹窗表单 | 审批节点表格内嵌编辑 | 同上 | 表单字段变为表格列 | 否，已替代 |

**⚠️ 关键规则**：
- 设计变更**只适用于用户明确要求改变**的场景，不允许 AI 自行将"未实现"标注为"设计变更"
- 即使设计变更替代了某个页面，**与该页面无关的功能仍需独立页面**（如：规则配置方式变了，但执行日志页仍然需要）
- 变更影响必须逐条分析，不能笼统地说"5.3-5.5全部替代"

#### 0.3 覆盖率计算（⛔ 强制规则）

```
覆盖率 = (✅已实现数 + ⚠️设计变更数) / (✅已实现数 + ⚠️设计变更数 + ❌未实现数)
分母 = 所有需要页面的 PRD 章节数（排除 ⬜不适用）
```

**⛔ 禁止的覆盖率计算方式**：
- ❌ 自行定义"功能清单总数"，不参考 PRD
- ❌ 只统计已实现的页面数作为分子和分母（导致永远100%）
- ❌ 将未实现的页面排除在分母之外
- ❌ 将"设计变更"等同于"不需要实现"（必须分析变更影响）

#### 0.4 通过标准

- **覆盖率 = 100%**：所有 PRD 章节都有对应原型（或合理的已标注设计变更）
- **覆盖率 < 100%**：自测不通过，必须在报告中列出未实现章节，并标注优先级（P0/P1/P2）
- **覆盖率报告中不得出现虚高的百分比**，如有未实现章节则覆盖率必须低于100%

#### 1.2 PRD → 原型一致性

对照PRD中的功能描述，检查原型是否实现。

**页面基础结构检查项**（新增页面必检）：
- [ ] **侧边栏可见**：侧边栏高度不为0，菜单完整显示（注意 `fill_container(0)` 在绝对定位布局中回退值为0）
- [ ] **侧边栏菜单高亮**：当前页面对应的菜单项高亮正确
- [ ] **面包屑文本正确**：面包屑路径与当前页面一致
- [ ] **主内容区背景色**：主内容区域有正确的背景色（通常为 `#F5F5F5`）

**列表页检查项**：
- [ ] **列表字段**：所有PRD中定义的列表字段都在原型中展示
- [ ] **搜索条件**：所有搜索条件都在原型中可操作
- [ ] **排序功能**：排序按钮/字段可点击
- [ ] **翻页功能**：翻页控件可操作
- [ ] **操作按钮**：所有操作按钮（新增、编辑、删除等）都存在

**表单页检查项**：
- [ ] **表单字段**：所有PRD中定义的字段都在原型中
- [ ] **字段类型**：控件类型正确（文本框/下拉框/日期选择器等）
- [ ] **必填标识**：必填字段有明确标识（*号或红色星号）
- [ ] **字段长度**：长文本字段有足够的空间
- [ ] **默认值**：默认值字段有预填内容

**按钮检查项**：
- [ ] **主操作按钮**：保存、提交、确定等按钮位置明显
- [ ] **次要操作按钮**：取消、重置等按钮存在
- [ ] **按钮状态**：禁用状态有视觉区分
- [ ] **按钮权限**：不同角色看到的按钮符合权限设计

| 状态类型 | 检查项 | 是否覆盖 | 说明 |

### 第三步半：节点替换样式一致性检查 ⭐ 新增

**目标**：确保使用 `R()` 替换组件实例后代节点时，新节点保留原有的容器样式

**触发条件**：每次使用 `R()` 操作替换节点后必须执行

**背景**：使用 `R()` 替换组件实例的后代节点时，新节点不会自动继承原节点的样式属性。如果遗漏关键样式（如白色背景、圆角、内边距），会导致卡片样式丢失，页面布局异常。

#### 检查清单

| 检查属性 | 常见默认值 | 说明 |
|---------|-----------|------|
| fill | `#FFFFFF` | 白色卡片背景色 |
| cornerRadius | `8` | 圆角半径 |
| padding | `20` | 内边距 |
| stroke | `{ fill: "#E5E7EB", thickness: 1 }` | 边框样式 |
| layout | `vertical` | 布局方向 |
| gap | `16` | 子元素间距 |
| width | `fill_container` | 宽度 |

**检查方法**：

1. 替换前，使用 `batch_get` 记录原节点的样式属性
2. 替换后，使用 `batch_get` 检查新节点是否包含所有必要样式
3. 使用 `get_screenshot` 视觉确认卡片样式完整

**❌ 错误示例**：
```javascript
// 替换时遗漏了卡片样式
```

### 第四步：表格设计专项检查 ⭐ 新增

**目标**：确保表格列宽均衡、对齐正确、视觉平衡

> **⛔ 强制规则**：这是原型设计中最常见的质量问题。每次创建或修改列表页表格后，必须执行此检查。列宽总和不等于1112px的原型不得通过自审。

#### 4.0 表格列宽快速验证（必做） ⛔ 强制

**在完成任何表格设计后，立即执行以下验证**：

1. 使用 `batch_get` 读取表格 thead 节点，获取所有列的 width 值
2. 计算所有列宽之和
3. 如果总和 ≠ 1112px，立即修复：
   - 参照 `rules/dayu-design-system.md` 5.4.3 常见列宽参考重新分配
   - 确保每列宽度合理（参考推荐范围）
   - 重新验证总和 = 1112px
4. 验证所有数据行（tr）的列宽与表头一致

**常见错误模式**：
- ❌ 从其他页面复制表格后只修改了列数/内容，没有重新计算列宽
- ❌ 减少列数后没有将释放的宽度分配给其他列
- ❌ 增加列数后没有从其他列收缩宽度
- ❌ 使用了过小的固定宽度（如60px、70px），导致总和远小于1112px

#### 4.1 表格列宽均衡检查 ⚠️ 重要

**检查工具**：使用 `mcp__pencil__snapshot_layout()` 工具

**检查步骤**：

1. **获取表格布局数据**
   ```javascript
   mcp__pencil__snapshot_layout({
     parentId: "{table-id}",
     maxDepth: 2
   })
   ```

2. **检查表头列宽**
   - 记录每列的 width 值
   - 检查是否有单列宽度 > 300px（警告）
   - 检查是否有单列宽度 > 400px（错误）
   - 计算所有列宽度之和是否 = 1112px

3. **检查数据行列宽**
   - 记录每个数据行的列宽
   - 验证数据行列宽与表头列宽一致
   - 允许 ±2px 的误差

4. **检查列 x 坐标对齐**
   - 记录表头每列的 x 坐标
   - 记录数据行每列的 x 坐标
   - 验证同一列的 x 坐标在表头和数据行中一致（±2px 误差可接受）

**检查清单**：

| 检查项 | 标准 | 通过 | 备注 |
|--------|------|------|------|
| 总宽度 = 1112px | 所有列宽度之和 = 1112px | ✅/❌ | 实际：___ px |
| 无过宽列 | 所有列宽度 ≤ 300px（内容列除外） | ✅/❌ | 最宽列：___ px |
| 表头数据对齐 | 表头和数据行 x 坐标一致 | ✅/❌ | 最大偏差：___ px |
| 列宽一致性 | 表头和数据行列宽一致 | ✅/❌ | 不一致列：___ |
| 视觉平衡 | 无明显宽窄差异 | ✅/❌ | ___ |

**常见问题识别**：

❌ **问题1：单列过宽**
- **症状**：某列宽度 > 400px，其他列相对过窄
- **原因**：使用 `fill_container` 导致该列占据所有剩余空间
- **修复**：改为固定宽度，重新分配所有列宽

❌ **问题2：列不对齐**
- **症状**：表头和数据行的 x 坐标不一致
- **原因**：表头和数据行使用了不同的列宽
- **修复**：统一表头和数据行的列宽配置

❌ **问题3：总宽度不正确**
- **症状**：所有列宽度之和 ≠ 1112px
- **原因**：列宽分配计算错误
- **修复**：重新计算并调整列宽

#### 4.5 隐藏列处理检查（强制） ⚠️ 重要

**目标**：确保从其他列表页复制并修改表格时，多余列被正确处理

**背景**：从已有列表页复制表格后，如果需要减少列数，必须彻底删除多余列节点。使用 `enabled:false` 或 `width:0` 隐藏列会导致隐藏列仍参与 `space_between` 布局分配，造成表头和数据行列不对齐。

**处理多余列的方式**：

| 方式 | 是否正确 | 原因 |
|------|---------|------|
| `D("nodeId")` 删除节点 | ✅ 正确 | 节点彻底移除，不参与布局 |
| `enabled: false` | ❌ 错误 | 节点仍参与 space_between 布局分配 |
| `width: 0` | ❌ 错误 | 节点仍占据布局位置 |
| `enabled: false` + `width: 0` | ❌ 错误 | 同上，两者叠加仍无法解决 |

**检查方法**：

1. 使用 `snapshot_layout` 获取表格布局数据
2. 确认表头子元素数量 = 数据行子元素数量
3. 确认没有 width=0 的子元素存在
4. 确认所有列的 x 坐标在表头和数据行之间一致（±2px）

**检查清单**：

| 检查项 | 标准 | 通过 | 备注 |
|--------|------|------|------|
| 表头子元素数 = 数据行子元素数 | 数量完全一致 | ✅/❌ | 表头：___ 个，数据行：___ 个 |
| 无 width=0 的子元素 | 所有子元素 width > 0 | ✅/❌ | ___ |
| 无 enabled=false 的隐藏列 | 所有列 enabled ≠ false | ✅/❌ | ___ |
| 列 x 坐标对齐 | 表头和数据行 ±2px | ✅/❌ | 最大偏差：___ px |

## 常见问题

### Q1：原型自审和需求文档自审有什么区别？

**A**：
- **原型自审**（阶段6.5）：侧重原型的完整性、可操作性、用户体验
- **需求文档自审**（阶段7）：侧重PRD文档的规范性、逻辑性、可执行性

两者侧重点不同，都必不可少。

### Q2：如果原型自审不通过，需要重新做原型吗？

**A**：
- **P0问题**（必须修复）：需要修复，但不一定重新做原型，通常在现有原型上修改
- **大量P0问题**（覆盖率<70%）：可能需要重新设计原型
- **通过率低**（<70%）：建议重新审视需求和功能设计

### Q3：原型自审需要多长时间？

**A**：
- 小型原型（1-3个页面）：30-60分钟
- 中型原型（4-10个页面）：1-2小时
- 大型原型（10+个页面）：2-3小时

建议预留充足时间，不要匆忙。

### Q4：自审报告需要保存吗？

**A**：**强烈建议保存**。

**保存位置**：`prd/{feature-name}/06-原型自测报告.md`

**价值**：
- 作为阶段7（需求文档自审）的输入
- 作为开发的参考
- 作为验收的依据
- 作为项目复盘的资料

## 最佳实践

### 1. 自审时机

- ✅ **原型完成后立即自审**：发现问题及时修复，避免遗忘
- ✅ **间隔一段时间后再审**：隔天或隔几个小时，用"用户视角"重新审视
- ❌ **不要在疲劳时自审**：疲劳容易遗漏问题

### 2. 自审方法

- ✅ **模拟真实用户操作**：把自己当成小白用户
- ✅ **记录所有发现的问题**：不要依赖记忆
- ✅ **使用检查清单**：确保不遗漏检查项
- ❌ **不要只看不动**：原型必须操作才能发现问题

### 3. 问题优先级

- **P0（必须修复）**：
  - 功能缺失
  - 操作流程中断
  - 无法完成主要任务

- **P1（建议修复）**：
  - 交互不流畅
  - 样式不统一
  - 提示不明确

- **P2（可选优化）**：
  - 美观度问题
  - 微小的交互优化

### 4. 改进建议

- 优先修复P0问题
- 尽量修复P1问题
- 可选优化P2问题
- 修复后重新自审相关项
