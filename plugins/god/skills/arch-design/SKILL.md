## 方案设计执行流程

按 [`tech-solution.md`](templates/tech-solution.md) 模板结构输出技术方案。

**前置输入：** 本流程由 `/architect` 命令调用。调用前 `/architect` 的 Phase 1 已完成知识加载（代码扫描 + 知识库读取），相关上下文已在对话中，无需重复加载。

### 执行流程

```
第一: API 接口 Brainstorming（主上下文交互）
    ↓
第二: DB 实体推导 + 去重校验（主上下文交互）
    ↓
Brainstorming 合并确认（一次性确认 API 接口 + DB 实体决策）
    ↓
第三: 接口文档生成（独立执行）
    ↓
第四: 数据库设计（独立执行）
    ↓
第五: 前端架构（当需求涉及前端页面时）
    ↓
第六: 组装技术方案主文档
    ↓
第七: 关键决策点确认
    ↓
输出前自检
```

## 第一：API 接口 Brainstorming

> 以下规则在主上下文中执行，用于与用户交互确认接口设计。

**场景判断**：
- 读 `biz-tech-docs/INDEX.md`，通过"任务 → 必读文件"路由表定位到相关模块文档，若文档中包含 Controller 信息 → "已有接口选取"
- INDEX.md 中无对应模块路由 → "全新模块设计"

### 已有接口选取

1. 从 INDEX.md 路由到的模块文档中获取 Controller 列表，然后扫描项目代码中对应 Controller 的所有端点（`@PostMapping`/`@GetMapping`），标注关联度（匹配/可能匹配/不太匹配），**禁止筛选**
2. 读对应 Response VO 文件补充返回字段信息，判断匹配度
3. 以表格呈现：# | 接口名 | 方法 | 路径 | 功能说明（原文） | 关联度 | 分析
4. 用户确认后锁定，后续严格使用确认结果

### 复用接口代码存在性验证（强制）

> 用户确认复用接口后、进入 Brainstorming 合并确认前，**必须**执行。防止知识库文档过时导致方案引用不存在的接口。

对每个用户确认的复用接口，Grep 项目代码验证其真实存在：

**验证方式**：
- Web ��口：Grep `@WebApiController` 所在文件中的 `@PostMapping("路径")` 或 `@GetMapping("路径")`
- Feign 接口：Grep `@ApiController` 所在文件中的 `@PostMapping("路径")` 或 `@GetMapping("路径")`

**验证结果处理**：
- ✅ 存在：正常锁定，进入后续流程
- ⚠️ 代码未找到：标注 `⚠️ 代码未找到`，提交用户决策（移除该接口 / 降级为"新增接口" / 标记"待验证"后继续）
- 🔀 路径不一致：标注实际代码路径，提交用户确认使用文档路径还是代码路径

**验证通过后才能进入 Brainstorming 合并确认。**


### 全新模块设计

1. 从 PRD + UI 提取所有用户操作场景
2. 提出 ≥2 种接口划分方案（按资源 vs 按业务域），对比推荐
3. 用户确认方案后列完整接口清单
4. 搜索可复用的通用接口（企业信息、用户信息等）
5. 对找到的可复用接口，执行"复用接口代码存在性验证（强制）"，验证通过后进入主管道的 Brainstorming 合并确认

### 接口类型区分

| 类型 | 注解 | 标识特征 |
|------|------|---------|
| Web 接口 | `@WebApiController` | 路径不含 `/api/` |
| Feign 接口 | `@ApiController` | 路径含 `/api/` |

**可复用接口前置检查**：查询知识库已有接口和资源清单，确认是否有可提供下拉/字典数据的已有接口，直接纳入"复用接口"。

**Brainstorming 合并确认**：

将 API 接口候选清单 + DB 实体/复用决策合并为一次用户确认：
- 可复用资源一致性检查：对可复用数据源清单每一项，在 API 候选清单和 DB 实体决策中搜索引用，未引用项必须作为独立确认项
- 先输出 markdown 表格到对话，再用 AskUserQuestion 确认

## 第二：DB 实体推导 + 去重校验

> 以下规则在主上下文中执行。

### 实体推导

1. 从 PRD 识别业务实体
2. 从接口请求/响应体提取数据字段，反推所需表
3. 结合现有代码 Entity 层完成状态，判断哪些表已存在

输出实体清单：序号 | 实体名 | 来源 | 状态（新增/已存在） | 说明

### 去重校验（强制）

对每个"新增"实体，搜索 4 维度：

1. Read `table_index.json` 后按关键词匹配定位。**禁止用 Glob 列出整个 sql_ddl 目录**
2. Grep 项目代码 Entity/Mapper 类名
3. Grep 知识库模块功能文档搜索业务概念
4. Grep 已有 Controller/VO/前端 hook 搜索数据源接口

输出：拟新增实体 | DDL 匹配 | 代码匹配 | 数据源复用 | 决策（确认新增/改复用/提交用户决策）

## 第三：接口文档生成

> Brainstorming 确认后，独立执行接口文档生成。本节定义任务规范。

**执行 skill**：`api-creator`，从 Step 4 开始执行。

**输入**：
1. 已确认的接口清单：`{接口名 | 方法 | 路径 | 服务 | 类型 | 说明}`
2. 每个接口的字段推导：`{请求字段(名称/类型/必填/约束)、响应字段(名称/类型/说明)}`
3. 业务规则摘要：`{逐接口关键规则，标注 PRD 来源章节}`
4. 工作目录：`$WORK_DIR`
5. 上下文：对于接口生成有关联的所有内容，全部输出，不做摘要

**输出**：`$WORK_DIR/design/api/*.md`（每个接口一个文件），文件路径列表 + 文件数量。

**验证**：`ls design/api/*.md | wc -l` 确认数量与接口清单一致。

## 第四：数据库设计

> 实体确认后，独立执行数据库设计。本节定义任务规范。

**执行 skill**：`db-migration`，从 Step 2 开始执行。

**输入**：
1. 已确认的实体清单（含去重决策）：`{实体名 | 状态 | 决策}`
2. 接口设计字段摘要：`{逐接口请求/响应关键字段}`
3. 每个实体的字段推导：`{字段名/类型/约束/说明}`
4. 工作目录：`$WORK_DIR`
5. 上下文：对于数据库设计有关联的所有内容，全部输出，不做摘要

**输出**：`$WORK_DIR/design/db/db.md` + `$WORK_DIR/design/sql/*.sql`，文件路径列表 + 表数量 + 是否需要历史数据兼容确认。

**后处理**：
如返回需要历史数据兼容确认，在主上下文执行兼容方案 Brainstorming（参考 db-migration 的"历史数据兼容方案 Brainstorming 规范"核心要点：枚举变更影响 → 呈现候选方案 → 用户确认），确认后再次执行兼容方案输出。

## 第五：前端架构（当需求涉及前端页面时）

- 按模板第 8 章结构输出前端架构（路由规划、组件结构、差异化策略等）
- 涉及技术组件选型时，加载 `tech-selection` skill 执行选型 Brainstorming
- **非标准 UI 模式必须选型**：原型中存在标准组件无法覆盖的 UI 模式时，必须执行 Brainstorming

## 第六：组装技术方案主文档

将以上产物组装为 `tech-design.md`，同时将 DB 设计写入 `design/db/db.md`。

## 第七：关键决策点确认

在上述 Brainstorming 完成后，确认业务逻辑主流程和关键设计决策（仅当无明确先例时）。

**格式要求**：每个决策项 ≥3 个候选方案，表格对比，用户确认后锁定。

**典型决策类型**：外部系统对接架构、并发控制、数据一致性、批量操作拆分、状态模型、安全方案。

## 技术方案内容要点

技术方案不允许包含代码（伪代码除外），应包含：

- **现有代码基础**：分析已有代码，标注各层完成状态
- **微服务划分**：涉及服务、代码库路径、依赖关系
- **后端架构**：Service 分层、跨模块映射、新增文件清单
- **API 接口**：第三步产出
- **处理流程**：核心业务流程，标注跨服务调用链路
- **流程图**：多步骤/跨服务/有条件分支时必须输出（Mermaid flowchart/sequenceDiagram）
- **状态机图**：实体 3+ 状态/流转有约束/PRD 有状态定义时必须输出（Mermaid stateDiagram-v2）
- **历史数据兼容方案**：涉及现有表变更时必填（第四步产出）
- **前端架构**：涉及前端页面时必填
- **数据校验规则**：涉及数据校验时必填
- **异常处理**：所有异常场景、处理方式、前端提示文案
- **分布式微服务管理**：涉及多个服务时必须明确各自代码库路径和调用链路

## 输出前自检

> **上下文保护**：自检时对已生成的文件优先用 Grep 搜索关键内容确认，避免 full Read 重复加载整个文件。

- [ ] **API**：总览表列与模板一致（新增/修改表含：接口、方法、路径、所属服务、**接口描述**、说明、接口明细；复用表含：接口、方法、路径、所属服务、**接口描述**、接口类型、来源文档、复用场景说明、接口明细）、明细文档已生成且无占位符、路径与 brainstorming 确认一致、下拉/字典数据源已检查复用、**复用接口已通过代码存在性验证**
- [ ] **DB**：去重校验已执行、表结构含必备字段（id/biz_key/create_time/update_time/is_deleted/deleted_time）、biz_key 关联、金额 DECIMAL(18,2)
- [ ] **文档**：tech-design.md 含完整 1-10 章、流程图（多步骤/跨服务时）、状态机图（3+ 状态/有约束时）
- [ ] **一致性**：API-DB 字段对齐、服务-module 对齐、状态值/枚举值跨文档一致
- [ ] **用户确认**：API brainstorming、历史数据兼容（如有）、关键决策均已确认

## 终止条件

先自检，然后执行终止确认。以下条件**全部满足**时才算完成：

- [ ] `design/tech-design.md` 已写入，包含完整的 1-10 章
- [ ] `design/db/db.md` 已写入，包含所有涉及表的 DDL + 去重校验记录
- [ ] `design/api/` 目录下已生成全部新增接口的明细文档
- [ ] tech-design.md 第 3 章接口总览表列与模板定义完全一致（逐表核对列名），每个接口有「接口明细」列链接，且链接对应的文件存在
- [ ] 方案自检清单已全部通过
- [ ] 方案评审已通过（≥90分）
