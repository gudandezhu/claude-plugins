# 系统化调试

## 铁律

```
没有根因调查，就不能提出修复方案。
```

如果你还没完成阶段一，就不能动手修代码。

## 何时使用

遇到以下任何情况时必须使用：
- 测试失败
- 运行时报错
- 行为与预期不符
- 性能异常
- 构建失败

**尤其是**当你觉得"改一下就好了"的时候 — 这正是需要系统化调试的信号。

## 四个阶段

必须按顺序完成，不能跳过。

### 阶段一：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过报错和警告
   - 完整阅读堆栈跟踪
   - 记录文件路径、行号、错误码

2. **稳定复现**
   - 能否每次都触发？
   - 精确的复现步骤是什么？
   - 不能复现 → 收集更多数据，不要猜

3. **检查最近变更**
   - `git diff` 和最近的提交
   - 新增的依赖、配置变更
   - 环境差异

4. **追踪数据流**
   - 错误值从哪里来？
   - 谁传入了错误的参数？
   - 一直往上追溯，直到找到源头
   - 在源头修复，不在症状处修复

### 阶段二：模式分析

1. **找到正常工作的类似代码**
   - 同一项目中有没有类似的、能正常工作的代码？

2. **对比差异**
   - 正常的和异常的之间有什么不同？
   - 列出所有差异，不要假设"这个不重要"

3. **理解依赖**
   - 这段代码依赖什么组件、配置、环境？
   - 有什么隐含的前提条件？

### 阶段三：假设验证

1. **提出一个假设**
   - 明确陈述："我认为根因是 X，因为 Y"
   - 必须具体，不能模糊

2. **最小化验证**
   - 做最小的改动来验证假设
   - 一次只改一个变量
   - 不要同时修多个东西

3. **判断结果**
   - 验证通过 → 进入阶段四
   - 验证失败 → 提出新假设，不要在失败的假设上叠加修改

### 阶段四：实施修复

1. **先写失败测试**
   - 写一个能复现 bug 的测试
   - 确认测试失败
   - 使用 `tdd` 技能的 RED-GREEN-REFACTOR 流程

2. **修复根因**
   - 只改一个地方
   - 不要"顺便"改其他代码
   - 不要捆绑重构

3. **验证修复**
   - 测试通过了？
   - 其他测试没被破坏？
   - 问题真的解决了？

4. **连续失败 3 次？停下来**
   - 如果已经尝试了 3 次修复都没成功
   - **停止修复，质疑架构**
   - 这不是假设错了，是方向错了
   - 向用户说明情况，讨论是否需要重新设计

## 危险信号 — 立即停下

如果你发现自己在想：

| 想法 | 现实 |
|------|------|
| "先试试改这个" | 没有根因调查就是猜测 |
| "应该是这个问题" | "应该"不是证据 |
| "快速修一下" | 快速修复 = 慢速调试 |
| "同时改几个地方试试" | 无法判断哪个改动有效 |
| "再试一次同样的方法" | 已经失败的方法不会突然成功 |
| "跳过测试，手动验证" | 手动验证不可重复 |

**以上想法出现 = 停下来，回到阶段一。**
