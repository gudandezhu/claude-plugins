# API 接口文档生成 Skill

## 调用约定

调用时需提供以下输入：
- 已确认的接口清单（表格）
- 每个接口的字段推导结果（请求/响应字段 + 类型 + 约束）
- 业务规则摘要（来源章节标注）
- 工作目录路径

若 Brainstorming 已在调用方完成，**跳过 Brainstorming 部分**，直接从"接口文档生成流程" Step 4 开始，为每个接口按模板生成明细文档。

## 核心原则

1. **原型驱动**：从原型 HTML 中逐页面提取交互操作，反推所需接口，确保接口与 UI 一一对应
2. **PRD 补充业务规则**：接口的业务规则、校验规则、异常场景来源于 PRD，标注来源章节
3. **总览 + 明细分离**：tech-design.md 中写接口总览表（含明细文档链接），明细文档输出到 `design/api/`
4. **仅 GET/POST**：只允许 GET/POST 请求，不允许 PUT、DELETE 请求
5. **API 接口用户确认**：API 接口必须经过 brainstorming 枚举 + 用户确认，AI 不自行决定

## 产物路径

| 产物         | 输出路径                                                        | 说明                                                                     |
| ------------ | --------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 接口总览表   | `$WORK_DIR/design/tech-design.md` 第 3 章                     | 含明细文档相对路径链接                                                   |
| 接口明细文档 | `$WORK_DIR/design/api/{HTTP方法}-{路径简写}.md`             | 每个接口独立文件，使用[`templates/api-doc.md`](templates/api-doc.md) 模板 |

工作目录：`$WORK_DIR` = `$JLC_AI_WORKSPACE/process-docs/{需求编号}`。

## API 接口 Brainstorming 规范

> 本规范在 `arch-design` skill 的"第一：API 接口设计"中被调用。

### 核心原则

**API 接口的选取和设计不允许由 AI 自行决定，必须通过 brainstorming 枚举 + 用户确认流程。**

原因：LLM 在面对多个名称/功能相似的接口时，容易基于模糊匹配选错接口。即使有详细的规则指导，LLM 的"选择"行为本身不可靠。brainstorming 模式将"选择权"交给用户，AI 只负责"枚举和呈现"。

### 接口类型区分

| 类型                 | 注解                  | 用途                              | 标识特征                                  |
| -------------------- | --------------------- | --------------------------------- | ----------------------------------------- |
| **Web 接口**   | `@WebApiController` | 面向前端的 HTTP REST 接口         | 基础路径不含 `/api/`，文档标注 `Web`  |
| **Feign 接口** | `@ApiController`    | 微服务间内部调用接口（OpenFeign） | 基础路径含 `/api/` 或文档标注 `Feign` |

### Brainstorming 流程（已有接口选取场景）

适用于：通过 `biz-tech-docs/INDEX.md` 路由表定位到相关模块文档，文档中包含 Controller 信息，需要从中选取已有接口的场景。

#### Step 1: 枚举（AI 执行，不筛选）

1. 读 `biz-tech-docs/INDEX.md`，通过"任务 → 必读文件"路由表定位到相关模块文档
2. 从模块文档中获取 Controller 列表（Controller 名 + 路径 + 类型）
3. 扫描项目代码中对应 Controller 文件，提取**所有端点**（`@PostMapping`/`@GetMapping`），得到完整接口列表

**枚举规则：**

- 列出该模块的**所有接口**，不跳过任何一条
- 对每条接口标注与需求的**关联度判断**：
  - **匹配**：功能明确匹配需求场景
  - **可能匹配**：名称或功能部分匹配，需用户判断
  - **不太匹配**：功能差异较大，但作为参照列出
- **禁止在枚举阶段做筛选**，宁可多列不可遗漏
- **读取 Response VO 文件**（`{项目}/src/main/java/.../api/vo/resp/{VO名}.java`），通过返回字段（特别是嵌套对象列表如 `xxxList`）判断接口是否真正匹配需求

#### Step 2: 呈现候选清单（供用户确认）

以结构化表格呈现所有候选接口，格式：

```
## API 接口候选清单

来源：INDEX.md → {模块文档} → 项目代码扫描

| # | 接口名 | 方法 | 路径 | 功能说明（文档原文） | 关联度 | 分析 |
|---|--------|------|------|---------------------|--------|------|
| 1 | menuPage | POST | /inventory/purchaseRequisitionDetail/menuPage | 菜单分页 | 可能相关 | 列表分页用途，按条件返回明细分页数据 |
| 2 | requisitionPurchaseDetail | POST | /inventory/purchaseRequisitionDetail/requisitionPurchaseDetail | 采购明细查询 | 相关 | 按请购单ID查询具体物料明细数据 |
| 3 | ... | ... | ... | ... | ... | ... |

请确认哪些接口应该作为API 接口（回复编号，如 "1,2" 或 "仅2"）：
```

#### Step 3: 用户确认后仍存疑时，从代码补充

- 如果用户认为所有候选都不对，或用户要求从代码重新查找
- **从项目代码中扫描 Controller 文件**，定位所有 `@PostMapping` / `@GetMapping` 端点及其返回 VO 类型
- 读取 Response VO 文件，获取完整字段列表（含嵌套对象如 `xxxList`）
- 重新呈现基于代码的候选清单

#### Step 4: 用户确认后锁定

- 用户确认后，将选定接口记录为最终API 接口
- 后续技术方案中**严格使用用户确认的接口**，不得自行增删或修改路径

#### Step 5: 复用接口代码存在性验证（强制）

> 用户确认复用接口后、进入 Brainstorming 合并确认前，**必须**执行。防止知识库文档过时导致方案引用不存在的接口。

对每个用户确认的复用接口，Grep 项目代码验证其真实存在：

- Web 接口：Grep `@WebApiController` 所在文件中的 `@PostMapping("路径")` 或 `@GetMapping("路径")`
- Feign 接口：Grep `@ApiController` 所在文件中的 `@PostMapping("路径")` 或 `@GetMapping("路径")`

**验证结果处理**：
- ✅ 存在：正常锁定
- ⚠️ 代码未找到：标注 `⚠️ 代码未找到`，提交用户决策（移除 / 降级为"新增接口" / 标记"待验证"）
- 🔀 路径不一致：标注实际代码路径，提交用户确认

### 常见错误警示

| 错误模式       | 示例                                                 | brainstorming 如何避免             |
| -------------- | ---------------------------------------------------- | ---------------------------------- |
| 模糊匹配选错   | 选了 `menuPage` 而非 `requisitionPurchaseDetail` | 两个都会列出并标注分析，由用户判断 |
| 混淆 Web/Feign | 前端场景选了 Feign 接口                              | 枚举时标注接口类型，用户可识别     |
| 凭猜测编造路径 | 路径拼写错误                                         | 路径从文档原文复制，不允许手写     |
| 遗漏可用接口   | 只找到一个而遗漏另一个更合适的                       | 枚举所有候选，宁多勿漏             |
| 复用接口不存在 | 知识库文档过时，引用已删除/重命名的接口              | Step 5 代码存在性验证，Grep Controller 确认端点存在 |

### 全新模块接口设计 Brainstorming 流程

适用于：`biz-tech-docs/INDEX.md` 中无对应模块路由，或路由到的文档中不包含 Controller 信息（全新业务模块），API 接口全部为新增设计。

#### Step 1: PRD 业务场景分析（AI 执行）

1. 从 PRD 中提取所有**用户操作场景**（如"配置银行参数"、"查询余额"、"发起支付"）
2. 从原型/UI设计稿中提取所有**页面交互操作**（按钮、表单提交、列表加载等）
3. 合并去重，得到完整的业务操作清单

**输出格式：**

| # | 业务场景     | 来源页面   | 操作描述             | 涉及数据实体 |
| - | ------------ | ---------- | -------------------- | ------------ |
| 1 | 银行配置管理 | 企业信息页 | 增删改查银行直联配置 | 银行配置     |
| 2 | ...          | ...        | ...                  | ...          |

#### Step 2: 接口划分方案枚举（AI 执行，至少提供 2 种划分方案）

对 Step 1 的操作清单，按功能域分组并提出接口划分方案。**必须提供至少 2 种划分方案**供对比。

**划分维度：**

- 按资源/实体分组（如 /bank/config/*, /bank/account/*）
- 按业务操作分组（如 /bank/query/*, /bank/payment/*）
- 粗粒度 vs 细粒度（如单个通用接口 vs 多个专用接口）

**呈现格式：**

```
## 全新模块接口划分方案

### 方案A（推荐）：按资源+操作混合划分
- /bank/config/* — 配置管理（5个接口）
- /bank/account/* — 结算账户管理（3个接口）
- /bank/transaction/* — 账务查询（4个接口）
- /bank/payment/* — 支付转账（8个接口）
合计：20个接口

### 方案B：按业务域划分
- /bank/setup/* — 开通配置（8个接口）
- /bank/finance/* — 财务操作（12个接口）
合计：20个接口

### 对比
| 维度 | 方案A | 方案B |
|------|-------|-------|
| 路径语义清晰度 | 高（资源导向） | 中（域导向） |
| 与项目现有风格一致性 | 高（与现有模块一致） | 低（新风格） |
| 前端调用直观性 | 高 | 中 |

**推荐：** 方案A — 理由：{具体原因}

请确认选择哪个方案（回复编号）：
```

#### Step 3: 用户确认后生成接口清单

- 用户确认划分方案后，基于选定方案列出完整的接口清单
- 每个接口包含：方法、路径、功能说明、所属服务
- 用户可调整个别接口后锁定

#### Step 4: 复用接口 Brainstorming

即使是全新模块，仍可能存在可复用的现有接口（如获取企业信息、获取用户信息等）。对这部分接口：

- 从知识库搜索可能匹配的现有接口
- 按上文"已有接口选取场景"的 Step 1-5 流程执行 Brainstorming（含代码存在性验证）
- 用户确认后标记为"复用接口"

## 接口文档生成流程

> 本流程在 `arch-design` skill 的"第一：API 接口设计"中被调用。

### Step 1: 加载上下文

读取以下文档（**必须在生成任何接口前完成**）：

- `$WORK_DIR/requirement/PRD/*` — 需求文档，提取业务规则、数据实体、校验规则
- `$WORK_DIR/requirement/UI/*.html` — 原型 HTML，逐页面提取交互操作
- API 接口确认结果（Brainstorming 流程中用户已确认的接口清单）

### Step 2: 原型交互分析 → 接口推导

逐页面分析原型 HTML，按以下规则推导接口：

**分析维度：**

- **列表页**：推导分页查询接口（GET/POST）、搜索条件
- **表单页**：推导新增/编辑提交接口（POST）
- **详情页**：推导详情查询接口（GET/POST）
- **操作按钮**：推导业务操作接口（审批、删除、导出等）
- **下拉/选择器**：推导数据字典或远程搜索接口

**输出接口清单草案：**

| 序号 | 来源页面   | 交互操作  | 推导接口     | 方法 | 预估路径                  | 说明           |
| ---- | ---------- | --------- | ------------ | ---- | ------------------------- | -------------- |
| 1    | 员工列表页 | 搜索+分页 | 员工分页查询 | POST | /basic/employee/pageQuery | 按条件分页查询 |
| 2    | 员工列表页 | 点击新增  | 员工新增     | POST | /basic/employee/add       | 新增员工       |

### Step 3: 归并去重 & 分类

将 Step 2 的接口清单按以下维度归并：

1. **去重**：同一页面多个交互指向同一接口时合并
2. **分类**：
   - **新增接口**：PRD 中明确提出的新功能
   - **修改接口**：现有接口需要增加字段或修改逻辑
   - **复用接口**：已有接口可直接满足需求（必须经过 Brainstorming 确认）

### Step 4: 生成接口明细文档

创建目录 `$WORK_DIR/design/api/`，针对新增和修改接口逐个按模板 [`templates/api-doc.md`](templates/api-doc.md) 生成明细文档。

- 命名规则：`{HTTP方法}-{路径简写}.md`，如 `POST-employee-pageQuery.md`
- API 接口：直接链接到知识库原文档，不需要生成明细文档

**生成要求**：

- 基本信息：接口路径、所属模块、版本
- 请求定义：Headers、路径参数、查询参数、请求体（含字段类型/必填/约束）
- 响应定义：成功响应结构（data 字段不允许留 `{}` 空对象）、失败场景（覆盖所有错误场景）
- 业务规则：从 PRD 提取，标注来源章节
- 调用示例：curl 命令使用真实路径和参数值
- 所有 `<!-- REQUIRED -->` 区块必须填充实际内容，不允许残留占位符

### Step 5: 生成接口总览表

将分类后的接口按以下格式写入 tech-design.md 第 3 章，每个接口的「接口明细」列链接到 Step 4 生成的明细文档：

```markdown
## 3. API 接口设计

列出本次涉及的所有接口总览表。每个接口的详细定义（请求参数、响应参数、错误码、调用示例）见 `design/api/` 目录下各接口文档。

### 3.1 新增 API 接口

| 接口 | 方法 | 路径 | 所属服务 | 说明 | 接口明细 |
|------|------|------|---------|------|---------|
| 员工分页查询 | POST | /basic/employee/pageQuery | basic-service | 按条件分页查询 | [`POST-employee-pageQuery.md`](api/POST-employee-pageQuery.md) |
| 员工新增 | POST | /basic/employee/add | basic-service | 新增员工 | [`POST-employee-add.md`](api/POST-employee-add.md) |

### 3.2 需要修改的现有 API 接口

| 接口 | 方法 | 路径 | 所属服务 | 说明 | 接口明细 |
|------|------|------|---------|------|---------|

### 3.3 需要复用的 API 接口

> **以下接口已通过 brainstorming 候选枚举 → 用户确认流程选定���**
> 来源：`biz-tech-docs/INDEX.md` 路由定位 → 项目代码 Controller 扫描

| 接口 | 方法 | 路径 | 所属服务 | 接口描述 | 接口类型 | 来源文档 | 复用场景说明 | 接口明细 |
|------|------|------|---------|---------|---------|---------|------------|---------|
| xxx | POST | /xxx/xxx | xxx-service | 为什么要有这个接口 | Web | INDEX.md → {模块文档} | 查询xxx | 知识库原文档 |
```

### Step 6: 自检验证

**覆盖度检查：**

- [ ] 原型中每个页面的所有交互操作都有对应接口
- [ ] PRD 中提到的所有业务功能都有接口支撑
- [ ] 新增/修改/复用分类正确，无遗漏

**明细文档质量检查：**

- [ ] 所有 `<!-- REQUIRED -->` 区块已填充实际内容，无残留占位符
- [ ] 请求体字段表格列出所有字段，且每个字段有类型、必填、约束说明
- [ ] 失败场景覆盖 PRD 中所有错误场景
- [ ] curl 命令使用真实路径和真实参数值
- [ ] 成功响应包含真实字段值（不允许 `{}` 空对象）

**一致性检查：**

- [ ] 总览表中「接口明细」链接与 `design/api/` 下文件一一对应
- [ ] API 接口路径与 brainstorming 用户确认的完全一致（原文复制）
- [ ] 接口路径遵循项目既有 URL 命名规范
- [ ] 接口所属服务与微服务划分章节一致

不通过则回到对应 Step 修正。
