# 提取验收标准 (AC)

## AC 定位

AC 是**验收兜底文档**，不是技术方案，也不是测试用例。

它在 zcode 开发流程中的角色是**唯一的"对/不对"裁判标准**：
- 需求分析阶段：AC 确认"做什么"
- 技术设计阶段：技术方案必须能解释如何满足每条 AC
- 编码阶段：代码实现必须通过每条 AC 的检验
- 测试阶段：测试用例从 AC 衍生，确保每条 AC 都有对应测试

因此 AC 只包含**"系统应该怎样"的断言**，不包含接口设计、数据模型、实现方案等技术细节，也不包含"如何验证"的测试步骤和测试数据。

## AC 写作原则

### 原则 1：每条 AC 必须完全可判定——结果可判定 + 过程可判定

**结果可判定**（Then 列必须有唯一的"通过/不通过"判定标准）：

| 禁止类型 | 错误示例 | 正确做法 |
|----------|---------|---------|
| "或"字句 | "菜单不可见**或**页面提示无权限" | 明确二选一："无权限用户不可见该菜单" |
| 条件性表述 | "**如业务允许**编辑已提交单据" | 明确结论："已提交至采购状态不显示编辑操作" |
| 模糊量词 | "数据聚合**正确**" | 给出可引用的计算规则："按 [AC-RULE-XX] 计算" |
| 主观词 | "**友好**提示网络异常" | 给出具体文案："显示 Toast '网络异常，请检查网络连接'" |
| 未定义引用 | "以**实际权限配置**为准" | 明确预期结果，或标注 `[待确认]` 并说明确认人 |
| 混入待定项 | 同一条 AC 中部分字段标注"暂不验收" | 暂不验收的字段拆为独立条目，状态标为 `[PENDING]` |

**过程可判定**（AC-OP 和交互类 AC-FN 的 Then/When 列必须覆盖操作过程，禁止黑盒描述）：

| 禁止类型 | 错误示例 | 正确做法 |
|----------|---------|---------|
| 只写最终结果 | Then: "保存成功，版本号自动递增" | Then: "1) 点击保存后按钮进入 Loading 状态（不可重复点击）2) 保存完成 Loading 消失，显示 Toast '保存成功' 3) 画布标题区域版本号从 v1 递增为 v2 4) 画布仍处于可编辑状态" |
| 操作描述黑盒 | When: "拖入节点" | When: "从左侧节点面板按住'开始'节点拖动到画布区域，节点跟随鼠标移动并显示放置位置指示线，释放鼠标完成放置" |
| 无中间状态 | Then: "提示'请添加开始节点'" | Then: "1) 点击保存按钮后，画布中缺少的'开始'节点高亮闪烁（红色边框）2) 画布上方出现固定提示条 '请添加开始节点' 3) 不触发保存请求，画布数据不变" |

过程级断言的 3 个必检维度：

| 维度 | 说明 | 典型内容 |
|------|------|---------|
| 触发反馈 | 操作触发后系统的即时反馈 | Loading 状态、按钮禁用、光标变化、进度条 |
| 中间状态 | 操作过程中数据/UI 的阶段性变化 | 状态切换动画、部分更新、校验提示、高亮标识 |
| 终态确认 | 操作完成后的最终状态及对后续操作的影响 | Toast 提示、数据刷新位置、按钮状态变化、后续可操作性 |

### 原则 2：AC 是纯规则断言，不是测试用例

AC 描述"系统应该怎样"，测试用例描述"如何验证这个断言"。区别：

| AC（保留在本文档） | 测试用例（不在本文档） |
|-------------------|---------------------|
| 总数量 = SUM(各明细数量) | 给定3条明细数量为 500/500/100，验证总数量=1100 |
| 模式切换响应时间 ≤ 1秒 | 使用 Performance API 计时验证切换耗时 |
| 物料种类数 = COUNT(DISTINCT 物料ID) | 给定5条不同物料，验证种类数=5 |
| 采购单全部生成时显示"已生成"绿色标签 | 准备一个所有明细已关联采购单的请购单，验证显示绿色标签 |

**禁止在 AC 中写入：**
- 具体测试数据（如 "500+500+100+100+50=1250"）——改为纯公式规则
- 测试操作步骤（如 "多次来回切换 Tab"）——改为纯行为断言
- 测试场景设定（如 "使用拥有已知数据权限的测试账号"）——改为业务前置条件描述
- 具体攻击字符串（如 `' OR 1=1 --`）——改为安全规则描述

### 原则 3：复用内容集中定义，功能 AC 引用编号而非重复

**业务规则**：计算公式、状态枚举、字段格式等被多个功能模块引用的规则，在 AC 章节的"全局业务规则"子节集中定义一次（编号 AC-RULE-{NN}）。功能 AC 中引用规则编号，不重复定义。

**UI 样式**：颜色值、字号、间距等 UI 细节已在 UI-ELEM-{NN} 章节定义，AC 中只描述业务语义，样式引用 UI 编号。

> 错误：AC-FN-XX "显示'待提交至采购'状态标签，背景 #fff7e6，文字 #fa8c16"
> 正确：AC-FN-XX "显示'待提交至采购'状态标签（样式见 UI-ELEM-XX）"

### 原则 4：GOAL 与 AC 必须建立双向追溯关系

- 每个 GOAL 必须能追溯到覆盖它的 AC 条目
- 每条核心 AC 必须能追溯到它服务的 GOAL
- 通过 GOAL 追溯矩阵表实现

### 原则 5：AC-FN 和 AC-OP 使用 Given-When-Then 三段式

每条 AC-FN 和 AC-OP 必须显式包含 Given（前置条件）、When（触发操作）、Then（预期结果）。

**正例**：
| 编号 | Given（前置条件） | When（操作） | Then（预期结果） | 来源 |
| AC-FN-03 | 用户已登录且有退货审核权限，列表中存在≥2条待审核退货单 | 用户勾选多条退货单并点击"标记异常" | 所选退货单状态变更为"异常"，触发异常通知，列表刷新 | PRD 5.2 |

**反例**：
| 编号 | 前置条件 | 操作 | 预期结果 | 来源 |
| AC-FN-03 | - | 支持批量标记异常 | 标记成功 | PRD 5.2 |
问题：无 Given（不知道什么条件下操作）、Then 不可判定（"成功"是模糊词）。

Given 为空说明前置条件不清，Then 使用模糊词说明不可判定——两者都是质量红线。

## AC 编号规范

### 三层结构：GOAL / AC / UI

```
第一层：G-{N}           业务目标（不计入覆盖分母）
第二层：AC-{TYPE}-{NN}   业务验收标准
第三层：UI-{TYPE}-{NN}   UI 验收标准（样式/布局/动画）
```

### AC 前缀枚举（固定，跨需求不变）

| 前缀 | 类型 | 语义 | 覆盖分母 | 测试层级归属 | 表格列特征 |
|------|------|------|---------|------------|-----------|
| **全局规则类（不作为e2e验收）** | | | | | |
| AC-RULE-{NN} | 全局规则 | 状态枚举、计算规则、字段格式、权限模型 | ❌ excluded | 嵌入 E2E/Flow 步骤 | 按子类分表定义 |
| **功能验收类** | | | | | |
| AC-FN-{NN} | 功能验收 | 具体功能的前置条件→操作→预期结果 | ✅ e2e | E2E 主责 | 前置条件 \| 操作 \| 预期结果 |
| **操作类** | | | | | |
| AC-OP-{NN} | 业务操作 | 涉及数据写入/状态变更/跨实体联动的操作 | ✅ flow + e2e | Flow 主责（接口串联），E2E 辅助（UI 触发） | 前置条件 \| 操作 \| 预期结果 |
| **异常场景类** | | | | | |
| AC-ERR-{NN} | 异常场景 | 错误处理、容错、恢复 | ✅ shared | E2E（前端异常）+ API（接口异常） | 异常场景 \| 系统行为 \| 提示文案 |
| **非功能需求类（不作为e2e验收）** | | | | | |
| AC-NF-{NN} | 非功能需求 | 性能、安全、可用性 | ❌ excluded | 专项测试 | 指标 \| 条件 |

### UI 前缀枚举

| 前缀 | 语义 | 覆盖分母 | 归属 |
|------|------|---------|------|
| UI-IXD-{NN} | 具有交互操作的 UI 元素 | ✅ e2e | E2E |
| UI-ELEM-{NN} | UI 组件样式规格 | ❌ excluded | - |

### AC-FN 与 AC-OP 的区分标准

- **AC-FN**：展示类、查询类、筛选类、导航类、只读交互（Tab切换、模式切换、展开收起）
- **AC-OP**：涉及数据写入（新增/编辑/删除）、状态变更（提交/审批/撤回）、跨实体联动（生成采购单）

### Step 1.5: 业务场景分析（在生成 AC 之前执行）

在 Step 1 加载文档后、Step 2 生成 AC 之前，先完成以下三项分析。分析结果不输出为独立文件，但必须体现在最终 AC 的覆盖范围和深度上。

#### 分析 1：实体生命周期建模

从 PRD 中识别所有核心业务实体，为每个实体构建完整生命周期：

1. **识别实体**：从 PRD 的"功能模块"、"数据流转"、"业务流程"章节提取名词（如：请购单、采购单、场景、链路、指标）
2. **定义状态**：每个实体的所有可能状态（参考 PRD 的状态枚举描述）
3. **标注转换**：每个状态转换的触发操作和前置条件
4. **识别依赖**：实体间的依赖关系（如"链路"依赖"场景"，"指标"依赖"链路节点"）

每个实体必须覆盖以下 6 个生命周期维度：

| 生命周期维度 | AC 要求 | 示例 |
|------------|---------|------|
| 创建 | 创建的前置条件、创建过程反馈、创建后的初始状态 | AC-OP: 创建场景后场景列表立即显示新条目，健康状态为"正常" |
| 查看/读取 | 不同角色、不同状态下的查看差异 | AC-FN: 禁用状态场景在总览卡片中显示"已禁用"标签，数据不刷新 |
| 编辑/修改 | 可编辑的状态范围、编辑过程的数据校验、编辑后的状态变化 | AC-OP: 编辑已生效场景需二次确认，确认后进入编辑态，版本号不变 |
| 状态流转 | 每个合法状态转换的触发条件、连锁反应 | AC-OP: 禁用场景后，下属链路和指标停止计算，总览卡片显示"已禁用" |
| 删除/作废 | 删除的前置条件（依赖检查）、删除后的级联影响 | AC-OP: 删除有关联链路的场景时提示"存在关联链路，无法删除" |
| 跨实体联动 | 实体 A 状态变更对实体 B 的影响 | AC-OP: 场景启用后，总览页面的监控数据卡片从"暂无数据"变为显示实时指标 |

**产出**：实体的状态转换图（脑内或草稿），用于 Step 2 确保每条状态转换边都有对应 AC。

#### 分析 2：用户操作旅程梳理

从 PRD 的用户角色描述和业务流程章节，梳理每类用户的核心操作旅程：

1. **识别角色**：从 PRD 的权限模型、角色描述中提取（如：采购专员、部门负责人）
2. **梳理旅程**：每类用户从"打开系统"到"完成任务"的完整操作序列
3. **标注断点**：旅程中需要 AC 覆盖但 PRD 描述模糊的环节

**产出**：角色-旅程清单，用于 Step 2 确保端到端用户旅程的每个环节都有 AC。

#### 分析 3：跨模块交互识别

识别 PRD 中涉及多个模块协同的场景：

1. **模块边界**：从 PRD 章节结构识别功能模块划分
2. **跨模块数据流**：模块 A 的产出作为模块 B 的输入（如：场景配置→链路编排→指标配置→总览展示）
3. **跨模块状态联动**：模块 A 状态变更触发模块 B 的行为变化（如：禁用场景→下属指标停止计算→总览卡片状态变化）
4. **端到端链路**：从用户触发到最终结果的完整数据流转路径

**产出**：跨模块交互清单，用于 Step 2 确保每个跨模块交互点都有 AC 覆盖。

## AC-{TYPE}-{NN}（验收标准）

AC 章节包含以下子节：

### 2.1 全局业务规则（AC-RULE-{NN}）

**跨模块复用的"业务真理"集中定义在此，功能 AC 中引用编号。所有条目使用 AC-RULE-{NN} 统一编号。**

#### 状态枚举定义

```
| 编号 | 状态类型 | 状态值 | 语义说明 | UI 样式引用 | 来源 |
|----------|----------|--------|---------|------------|------|
| AC-RULE-01 | 请购单状态 | 待提交至采购 | 默认/初始状态 | UI-ELEM-XX | PRD X.X |
| AC-RULE-02 | 请购单状态 | 已提交至采购 | 已确认提交 | UI-ELEM-XX | PRD X.X |
| ... | ... | ... | ... | ... | ... |
```

- 所有状态值必须穷举，不留"等"字
- 如存在未定义状态值的兜底规则，需明确说明（如"未知状态显示原值文本+默认灰色标签"）

#### 计算规则

```
| 编号 | 规则名称 | 公式 | 精度/格式 | 来源 |
|----------|---------|------|----------|------|
| AC-RULE-XX | 物料种类数 | COUNT(DISTINCT 物料ID) | 整数 | PRD 5 |
| AC-RULE-XX | 总数量 | SUM(各明细数量) | 整数 | PRD 5 |
| AC-RULE-XX | 总金额 | SUM(各明细金额) | 保留2位小数 | PRD 5 |
| ... | ... | ... | ... | ... |
```

- 空值处理规则必须明确（如"空值/null 按0参与计算，同时显示'数据异常'标签"）
- 默认值规则必须明确（如"状态字段为空时默认显示'待提交至采购'"）

#### 字段格式规范

```
| 编号 | 字段 | 格式 | 最大长度 | 来源 |
|----------|------|------|---------|------|
| AC-RULE-XX | 请购单号 | QG+日期+序号 | 20字符 | PRD 4.3.1 |
| AC-RULE-XX | 创建时间 | YYYY-MM-DD | - | PRD 4.3.1 |
| ... | ... | ... | ... | ... |
```

- 字段精度须无歧义

#### 权限模型

```
| 编号 | 角色 | 可访问功能 | 数据范围 | 角色特有行为 | 来源 |
|----------|------|----------|---------|------------|------|
| AC-RULE-XX | 采购专员 | 全部功能 | 全部请购单 | 可生成采购单 | PRD 1.1, 2.1 |
| AC-RULE-XX | 部门负责人 | 全部功能 | 本部门请购单 | 可执行审批 | PRD 1.1, 2.1 |
| ... | ... | ... | ... | ... | ... |
```

- PRD 内部矛盾标注 `[待确认]`

### 2.2 功能验收标准（AC-FN-{NN}）

按功能模块分小节，表格列：

```
| 编号 | Given（前置条件） | When（操作） | Then（预期结果） | 来源 |
```

- **编号**：`AC-FN-{NN}`，全局顺序编号（如 AC-FN-01, AC-FN-02）
- **Given**：操作前的系统状态和业务条件（对应"在什么情况下"），不得为空
- **When**：用户或系统执行的具体动作（对应"执行什么操作"）
- **Then**：操作后的可判定断言（对应"系统应该怎样"），**禁止模糊词**
- **来源**：PRD 章节号（精确到最小章节号如 4.4.1）或"UI原型"

### 2.3 业务操作标准（AC-OP-{NN}）

涉及数据写入/状态变更/跨实体联动的操作，表格列：

```
| 编号 | Given（前置条件） | When（操作） | Then（预期结果） | 来源 |
```

- **编号**：`AC-OP-{NN}`，全局顺序编号（如 AC-OP-01, AC-OP-02）
- **Given**：操作前的业务状态，必须明确实体当前状态（如"退货单状态='待审核'"）
- **When**：触发数据变更的用户/系统动作
- **Then**：数据变更后的系统状态断言，必须包含状态变化描述
- **来源**：PRD 章节号

**AC-FN 与 AC-OP 提取范围（合计覆盖）：**
1. 所有功能点的正常流程
2. 边界条件（空数据、极大值、特殊状态组合、0条明细）
3. 异常场景（网络错误、权限不足、数据异常）→ 使用 AC-ERR-{NN}
4. 数据计算与校验规则（引用 AC-RULE-{NN} 编号）
5. 非功能需求（性能阈值作为业务断言）→ 使用 AC-NF-{NN}
6. GOAL 中声明的业务目标对应的验收场景
7. 状态变更后的系统行为（如 AI 识别完成后页面数据刷新机制）
8. 操作的完整流程（如"生成采购单"的跳转方式、数据传递）
9. 组合交互场景（如 Tab 切换+模式切换、筛选+翻页+模式切换）
10. 未定义值的兜底规则（如未知状态值的显示）
11. 实体生命周期闭环：每个核心实体的创建→查看→编辑→状态流转→删除/作废全链路（见 Step 1.5 分析 1）
12. 端到端用户旅程：从用户触发操作到系统完成响应的完整路径，至少覆盖每类角色 1 条（见 Step 1.5 分析 2）
13. 跨模块状态联动：实体 A 状态变更后对实体 B 的级联影响（见 Step 1.5 分析 3）
14. 操作过程的中间状态断言：AC-OP 的 Then 列必须覆盖触发反馈、中间状态、终态确认三个维度（见原则 1 过程可判定）

## UI-{TYPE}-{NN}（UI 验收标准）

按交互类型分两大类：

### UI-IXD-{NN}（交互类）

具有交互操作的 UI 元素验收标准：

```
| 编号 | 组件 | 交互行为 | 预期效果 | 来源 |
```

- **编号**：`UI-IXD-{NN}`，全局顺序编号
- **覆盖分母**：✅ e2e
- **示例**：按钮点击、下拉选择、Tab切换、筛选操作、分页操作、展开收起

### UI-ELEM-{NN}（样式类）

UI 组件样式规格验收标准：

```
| 编号 | 组件 | 验收项 | 规格值 | 来源 |
```

- **编号**：`UI-ELEM-{NN}`，全局顺序编号
- **覆盖分母**：❌ excluded
- **示例**：颜色值、字号、边距、背景色、状态标签样式

**提取范围：**
1. 布局结构（导航、工具栏、表格、分页）
2. 组件样式（颜色值、字号、边距、背景色值）
3. 交互状态（悬停、选中、禁用、加载中）→ UI-IXD
4. 状态标签（各状态的颜色值和文案）→ UI-ELEM
5. 动画与过渡效果 → UI-IXD
6. 空状态、加载态、错误态的展示

UI-{TYPE}-{NN} 是验收兜底的一部分，保留在本文档中。AC 章节中涉及样式时引用 UI-ELEM 编号，不重复定义色值。
