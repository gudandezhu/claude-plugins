# AC 多专家评审模块

## 设计理念

AC 的核心价值是**防止开发做偏业务需求**。评审的重点不是格式扣分，而是发现真正的业务风险。

传统单 reviewer + rigid checklist 模式的问题：
1. 一个 subagent 承载 6 个维度，每个维度只能浅尝辄止
2. 扣分机制引导 subagent 忙于"数问题"，忽略 P0 级业务风险
3. 无专家角色代入，发现不了只有专业视角才能看到的问题

本模块采用 **4 个并行专家 subagent**，每个专家只专注 1-2 个维度深度挖掘，主 agent 综合评分。

## 变量

调用时替换以下变量（键名与 `parallel-review.js` 的 `templateVars` 一致）：
- `prdPath` → 实际 PRD 文件路径
- `uiPath` → 实际 UI 原型文件路径
- `acPath` → 生成的 ac.md 路径

## Phase 1: 并行专家评审

使用 Agent 工具并行启动 4 个 general-purpose subagent，每个传入对应的专家 prompt。

### 专家 1: PRD 业务覆盖度专家

**评审角度：** AC 是否完整覆盖 PRD 的每一个业务需求，有没有功能点遗漏、操作流程断点。

**覆盖维度：** 覆盖完整性(20%) + 业务价值覆盖与追溯(15%)

**Prompt 模板：**

```
你是资深 ERP 业务分析专家。评审 AC 文档是否完整覆盖 PRD 的所有业务需求。

先依次读取：
1. PRD：prdPath
2. UI 原型：uiPath
3. AC：acPath

## AC 编号规范（评审参照）

AC 使用固定前缀编号，跨需求不变：
- AC-RULE-{NN}：全局规则（状态枚举、计算规则、字段格式、权限），不计入 e2e 覆盖分母
- AC-FN-{NN}：功能验收（展示/查询/筛选/导航/只读交互），计入 e2e 覆盖
- AC-OP-{NN}：业务操作（数据写入/状态变更/跨实体联动），计入 flow + e2e 覆盖
- AC-ERR-{NN}：异常场景（错误处理/容错/恢复），计入 shared 覆盖
- AC-NF-{NN}：非功能需求（性能/安全/可用性），不计入 e2e 覆盖分母
- UI-IXD-{NN}：交互类 UI 验收，计入 e2e 覆盖
- UI-ELEM-{NN}：样式类 UI 验收，不计入 e2e 覆盖分母

## 评审任务

### 1. PRD 需求覆盖率
逐条对照 PRD 每个章节的每个功能点、操作、业务规则，找出 AC 中遗漏的内容。

### 2. 操作流程闭环
检查每个操作的完整流程：触发条件 → 交互方式 → 数据传递 → 结果展示。找出只有触发没有结果的断点。

### 3. 角色/权限覆盖
PRD 中提到的每个角色（如采购专员、部门负责人、财务人员），其使用场景是否都有 AC 覆盖。权限模型（AC-RULE）中的角色是否与功能 AC（AC-FN/AC-OP）中的使用一致。

### 4. 关联业务覆盖
PRD 中提到的关联模块联动需求(如采购订单联动、库存管理联动)，AC 中是否有对应条目。

### 5. GOAL 追溯矩阵验证
- 每个 GOAL 在追溯矩阵中列出的 AC 编号是否真实覆盖该目标
- 是否有 GOAL 没有任何 AC 覆盖

### 6. AC-FN 与 AC-OP 分类合理性
检查 AC-FN 和 AC-OP 的分类是否正确：
- 涉及数据写入/状态变更的应归入 AC-OP，而非 AC-FN
- 纯展示/查询/只读交互的应归入 AC-FN，而非 AC-OP

### 7. 实体生命周期闭环检查
从 AC-RULE 的状态枚举和 AC-FN/AC-OP 的条目，构建每个核心业务实体的生命周期覆盖矩阵：
- 创建/新增是否有 AC 覆盖
- 查看/读取是否有 AC 覆盖（不同状态下查看差异）
- 编辑/修改是否有 AC 覆盖（可编辑状态范围）
- 状态流转是否有 AC 覆盖（每个合法转换）
- 删除/作废是否有 AC 覆盖（含级联检查）
- 跨实体联动是否有 AC 覆盖

遗漏的生命周期环节标记为 P0 或 P1。

### 8. 端到端用户旅程检查
检查 PRD 中描述的每类用户角色，是否至少有一条从触发到终态的端到端 AC 覆盖链。
例如"采购专员"的旅程：创建请购单→添加物料→提交→查看生成结果→查看采购单。
旅程中的每个环节必须有对应 AC，断链处标记为 P1。
```

### 专家 2: AC 可判定性专家

**评审角度：** 每条 AC 是否有明确的"通过/不通过"判定标准，是否混入了测试用例内容。

**覆盖维度：** 可判定性(25%) + AC/测试用例边界(10%)

**Prompt 模板：**

```
你是资深的验收标准质量审查专家。逐条审查 AC 文档中每一条 AC 的可判定性。

先读取 AC 文件：acPath
如需对照 PRD，读取：prdPath

## AC 编号规范（评审参照）

AC 使用固定前缀编号：
- AC-RULE-{NN}：全局规则
- AC-FN-{NN}：功能验收
- AC-OP-{NN}：业务操作
- AC-ERR-{NN}：异常场景
- AC-NF-{NN}：非功能需求

## 评审任务

逐条检查每条 AC，重点审查：

### 1. 禁止"或"字句
如果一条 AC 中出现"或"，导致两种结果都算通过，标记为问题。
示例："菜单不可见 **或** 页面提示无权限" → 不通过

### 2. 禁止条件性表述
判定依赖未定义的外部条件：
- "**如业务允许**" → 不通过
- "**以实际配置为准**" → 不通过
- "**以 UI 原型为准**" → 不通过（应明确当前结论）

### 3. 禁止模糊词
未量化的主观词：
- "数据聚合**正确**" → 不通过，应引用 AC-RULE 编号
- "**友好**提示" → 不通过，应给出具体文案
- "样式**区别于**正常状态" → 不通过，应引用 UI-ELEM 编号

### 4. 精度歧义
- "小数12位" → 不通过，应明确"小数部分最多12位"或"总有效位数12位"

### 5. 测试用例混入
- 具体测试数据（如 "500+500=1000"）→ 不属于 AC
- 测试操作步骤（如 "多次来回切换"）→ 不属于 AC
- 测试场景设定（如 "使用测试账号验证"）→ 不属于 AC
- 注意：性能阈值（≤1秒）、Toast 文案、数据规模前置条件 — 这些是合法的 AC 内容

### 6. 暂不定项处理
同一条 AC 中部分内容标注"暂不验收" → 应拆为独立条目标记 [PENDING]

### 7. 编号规范检查
- AC 编号是否使用统一前缀（AC-RULE/AC-FN/AC-OP/AC-ERR/AC-NF）
- UI 编号是否使用统一前缀（UI-IXD/UI-ELEM）
- 编号是否连续无跳跃

### 8. 操作深度检查（AC-OP 专项）
逐条检查 AC-OP 的 Then 列：
- 只描述最终状态（如"保存成功"）而无过程断言的 → 标记为 P1 问题
- When 列只写操作名称（如"拖入节点"）而无操作过程的 → 标记为 P2 问题
- 建议补充：触发反馈（Loading/禁用）、中间状态（进度/部分更新/高亮标识）、终态确认（后续可操作性）

逐条检查交互类 AC-FN 的 When 列：
- 涉及拖拽、连线、筛选等交互操作，When 列是否描述了操作过程（来源、操作方式、视觉反馈）
- 仅写操作名称的 → 标记为 P2 问题

## 输出格式

```
## 评分：X/100（按可判定性和AC/测试边界的扣分规则，换算为百分制）

## 问题逐条列出

### 可判定性问题

```
## AC 编号规范（评审参照）

- AC-RULE-{NN}：全局规则（状态枚举定义在此）
- AC-FN-{NN}：功能验收
- AC-OP-{NN}：业务操作（数据写入/状态变更）
- AC-ERR-{NN}：异常场景
- AC-NF-{NN}：非功能需求

## 评审任务

### 1. 状态组合矩阵
如果 AC-RULE 定义了多个状态维度（如请购单状态 × 采购单状态），构建完整的组合矩阵，标注哪些组合有 AC-FN/AC-OP 覆盖、哪些遗漏。

### 2. 数据边界
- 空数据（0条记录、0条明细、字段值为空）
- 极大值（超长文本、超大数字、超多明细行）
- 数据精度（金额精度溢出、数量为负数或0）
- 特殊字符（搜索框、输入框）

### 3. 并发与时序
- 快速连续操作（防抖/节流/竞态条件）
- 网络延迟、超时、断网恢复
- 多用户同时操作同一数据

### 4. 权限边界
- 角色切换时的数据刷新
- 跨数据范围访问
- 未登录 / Token 过期

### 5. UI 交互边界
- 浏览器刷新、前进/后退
- 分页边界（首页、末页、空页、单页）
- 展开/收起上限（大量明细同时展开）

### 6. 数据一致性
- 汇总数据与明细数据的实时一致性
- 明细被修改/删除后汇总数据是否更新
- 分页状态在模式切换后的行为

### 7. 异常场景完整性
- 检查 AC-ERR 章节是否覆盖了上述边界触发的异常
- 每个异常是否有明确的提示文案和恢复操作
```

```
### 1. 内容准确性

- 无残留占位符（TODO、TBD 等）

- AC-FN/AC-OP 中引用的 AC-RULE 编号是否存在
- AC 中引用的 UI-ELEM/UI-IXD 编号是否存在
- 追溯矩阵中引用的 AC 编号是否存在
```

## Phase 2: 综合评分（方法论参考）

> **注意**：本节为评分方法论参考。实际加权评分由 `parallel-review.js` workflow 执行（基于 experts 数组的 weight 做加权平均）。以下维度和扣分规则供专家评审时参考校准。

主 agent 收集 4 个专家报告后，按 6 维度综合评分：

| 维度 | 满分 | 评分来源 | 扣分规则 |
|------|------|---------|---------|
| 覆盖完整性 | 20 | 专家 1 报告 | PRD 功能点遗漏每处扣2分；操作流程断点每处扣1分；边界遗漏每处扣1分；组合交互遗漏每处扣0.5分；实体生命周期环节遗漏每处扣1分；端到端用户旅程断链每处扣1分；跨模块联动遗漏每处扣1分 |
| 可判定性 | 25 | 专家 2 报告 | "或"字句每处扣3分；条件性表述每处扣3分；模糊词每处扣2分；精度歧义每处扣2分；暂不定项混入每处扣1分；AC-OP Then 列只描述最终状态无过程断言每处扣1分 |
| AC/测试用例边界 | 10 | 专家 2 报告 | 测试数据混入每处扣1分；测试步骤混入每处扣1分；测试场景混入每处扣1分 |
| 结构规范性 | 15 | 专家 4 报告 | 编号前缀不规范每处扣0.5分；缺章节扣2分；编号不连续每处扣0.5分；来源引用错误每处扣0.5分；重复定义每处扣1分；残留占位符每处扣0.5分 |
| 准确性 | 15 | 专家 4 报告 | 内容不一致每处扣2分；数值错误每处扣2分；交叉引用错误每处扣1分 |
| 业务价值覆盖与追溯 | 15 | 专家 1 报告 | GOAL 无追溯扣3分；角色遗漏每处扣1分；端到端流程断点每处扣1分 |

### 评分原则

1. **以专家发现的问题为准**，不重复检查
2. **P0 问题直接影响总分**，P0 超过 3 个则自动不通过（无论总分）
3. **同一问题在多个维度被发现的，按较重维度扣分**（不重复扣）
4. 扣分不设下限（最低 0 分），不设上限（最高扣到维度满分）

### 通过标准
