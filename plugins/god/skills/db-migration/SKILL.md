# 数据库设计与历史数据迁移

## 调用约定

调用时需提供以下输入：
- 已确认的实体清单（含去重决策结果）
- 接口设计结果字段摘要
- 每个实体的字段推导（从接口请求/响应反推）
- 工作目录路径

若实体推导和去重校验已在调用方完成，**跳过 Step 1（实体推导）和 Step 1.5（去重校验）**，直接从 Step 2（加载已有表结构）开始执行数据库设计流程。

## 数据库设计规范
> 项目规范>团队规范>公司规范

编写数据库设计时，`$JLC_AI_WORKSPACE/tech-specs/sql-spec/sql-design-spec.md`，核心要点：

- **biz_key**：业务主键，表关联必须使用 biz_key 而非自增 id
- **关联字段命名**：关联其他表时，字段命名必须为 `{关联表业务含义}_biz_key`（如 `order_biz_key` 关联订单表），禁止使用 `xxx_id` 命名关联字段。命名即语义——通过什么关联就叫什么
- **必备字段**：id / biz_key / create_time / update_time / is_deleted / deleted_time
- **DECIMAL 精度**：金额字段统一使用 DECIMAL(18,2)
- **软删除**：通过 is_deleted + deleted_time 实现，禁止物理删除
- **字段命名**：下划线命名法，见名知义
- **索引规范**：合理创建索引，避免冗余索引

### 数据源路径

数据库表结构定义位于 `$JLC_AI_WORKSPACE/biz-tech-docs/INDEX.md`索引的文档中：

| 资源         | 路径                                                       | 说明                                                 |
| ------------ | ---------------------------------------------------------- | ---------------------------------------------------- |
| 表分类索引   | `db_design/table_index.json`                             | 表按业务域分类的索引，用于定位表                     |
| 表结构 DDL   | `db_design/sql_ddl/{schema}.{table_name}.md` | 单表完整字段定义（字段名、类型、默认值、约束、注释） |
| SQL 设计规范 | `tech-specs/sql-spec/sql-design-spec.md`                 | 公司级数据库设计规范                                 |

### 渐进式加载策略

不要全量扫描所有 DDL 文件，按以下策略渐进加载：

1. **定位表名**：根据需求PRD和API 接口分析中涉及的实体名称，推断可能涉及的表名
2. **读取索引**：Read `table_index.json` 确认表的存在和分类。**禁止用 Glob 列出整个 sql_ddl 目录**，应直接 Read 索引文件后用关键词匹配定位
3. **精确加载**：仅加载确认涉及的表的 DDL 文件
4. **关联加载**：如果变更涉及外键关联或 biz_key 关联，同时加载关联表

## 数据库设计生成流程

> 本流程在 `arch-design` skill 的"第二：数据库设计"中被调用。

### Step 1: 从 PRD + 接口设计推导数据实体

根据以下输入推导需要哪些表：

1. **PRD 业务实体**：从 PRD 中识别所有业务实体（如"请购单"、"请购单明细"）
2. **接口设计反推**：从 api-creator 生成的接口请求/响应体中提取数据字段，反推所需表结构
3. **已有代码基础**：结合 arch-design 中"现有代码基础"章节的 Entity 层完成状态，判断哪些表已存在

**输出数据实体清单：**

| 序号 | 实体名     | 来源         | 状态   | 说明         |
| ---- | ---------- | ------------ | ------ | ------------ |
| 1    | 请购单主表 | PRD 业务实体 | 新增   | 核心业务单据 |
| 2    | 请购单明细 | PRD 业务实体 | 新增   | 子表明细     |
| 3    | 员工表     | 接口反推     | 已存在 | 复用现有表   |

### Step 1.5: 新增表去重校验（强制执行）

> **本步骤不可跳过。** 根因：曾出现设计新增表时未发现系统中已存在同义表（如设计 `erp_bank_dict` 时未发现 `t_bank_info`），导致数据冗余和返工。

对 Step 1 中状态为"新增"的每个实体，**必须**执行以下去重校验，确认系统中确实不存在可复用的表：

**校验维度（四维度缺一不可）：**

| 维度 | 操作                                                                    | 路径/方法 |
|------|-----------------------------------------------------------------------|----------|
| 1. 数据库 DDL 索引 | 在 `biz-tech-docs/INDEX.md` 中按表名/业务关键词搜索                               | 如搜索"bank"发现 `t_bank_info` |
| 2. 项目代码实体 | 在 `projects/` 下 grep 新增实体的核心业务关键词（如类名、表名的关键词），查找是否有对应的 Entity/Mapper  | 如 grep "Bank" 发现 `BankInfo.java`、`BankInfoMapper.java` |
| 3. 业务知识库 | 在 `biz-tech-docs/INDEX.md` 中搜索相关的模块功能文档，确认是否有已有业务概念描述                   | 如搜索"银行"发现已有银行管理功能文档 |
| 4. 数据源/字典复用分析 | 在 `projects/` 下 grep 已有的 Controller/VO/前端 hook，搜索与新表业务域匹配的已有数据源接口和前端组件 | 如搜索"Bank"发现 `BankWebController`、`useBankDataList`，说明银行列表数据已有来源 |

**校验结果处理：**

| 校验结果 | 处理方式 |
|---------|---------|
| 四维度均无匹配 → 确认新增 | 标记为"新增"，继续 Step 2 |
| 发现同义现有表 → 改为复用/扩展 | 将状态从"新增"改为"已存在"，记录现有表名和差异字段，进入 Step 4（设计现有表变更）|
| 发现部分重叠 → 提交用户决策 | 列出现有表和新增表的字段对比，提供 3 个候选方案（扩展现有表 / 部分复用+部分新增 / 完全独立），等用户确认 |
| 发现同义数据源但表结构不同 → 标记为数据源复用 | 表本身确需新增（字段维度不同），但其中的字典/下拉数据应复用已有数据源接口，在设计中明确标注复用关系 |

**去重校验输出格式（写入 db.md）：**

```markdown
### 新增表去重校验记录

| 拟新增实体 | DDL索引匹配 | 代码实体匹配 | 数据源复用分析 | 决策 |
|-----------|------------|-------------|--------------|------|
| 银行字典 | t_bank_info（银行字典表） | BankInfo.java + BankInfoMapper.java | BankWebController（银行列表接口）、useBankDataList（前端 hook） | 改为扩展 t_bank_info（+4字段），银行下拉数据复用已有接口 |
| 支付记录 | 无匹配 | 无 | 无 | 确认新增 |
```

### Step 2: 加载已有表结构

对"已存在"状态的表，按渐进式加载策略获取当前 DDL：

1. 读取 `table_index.json` 定位表
2. 加载对应 DDL 文件
3. 分析与需求的差异，确定是否需要变更

### Step 3: 设计新增表结构

对"新增"状态的表，按以下步骤设计：

1. **字段推导**：从 PRD 业务规则 + 接口请求/响应体推导字段列表
2. **规范校验**：逐字段检查是否符合 sql-design-spec.md 规范
3. **关联设计**：确定主子表关联方式（biz_key），关联字段命名为 `{关联表业务含义}_biz_key`（如 `order_biz_key`），禁止用 `xxx_id`
4. **索引设计**：根据查询场景设计索引

**新增表输出格式**（写入 `$WORK_DIR/design/db/db.md`）：

```markdown
# {表名}（{表说明}）

| 字段名 | 类型 | 默认值 | 约束 | 说明 |
|--------|------|--------|------|------|
| id | BIGINT | - | PK, AUTO_INCREMENT | 主键 |
| biz_key | VARCHAR(64) | - | UK, NOT NULL | 业务主键 |
| ... | ... | ... | ... | ... |

**索引设计：**
| 索引名 | 类型 | 字段 | 说明 |
|--------|------|------|------|
| uk_biz_key | UNIQUE | biz_key | 业务主键唯一索引 |
```

### Step 4: 设计现有表变更

对需要变更的现有表，列出变更清单（追加到 `$WORK_DIR/design/db/db.md`，标注变更类型）：

| 表名 | 变更类型                   | 变更内容 | 风险等级 |
| ---- | -------------------------- | -------- | -------- |
| ...  | 新增字段/修改字段/新增约束 | ...      | 低/中/高 |

### Step 5: 输出历史数据兼容方案

如果 Step 4 中存在中/高风险变更，加载下方"历史数据兼容方案 Brainstorming 规范"的用户确认结果，输出完整兼容方案（追加到 `$WORK_DIR/design/db/db.md`）。

如无历史数据兼容需求，写明"本次需求无历史数据兼容需求"。

### Step 5.5: 脚本自动校验（强制执行）

运行公司规范校验脚本：

```bash
node "$CLAUDE_PLUGIN_ROOT/scripts/db-design/validate-db-design.js" \
  --db-md "$WORK_DIR/design/db/db.md"
```

**脚本校验公司规范**（`$JLC_AI_WORKSPACE/tech-specs/sql-spec/sql-design-spec.md`），涵盖 12 个维度：必备字段、必备索引、金额字段类型、关联字段命名、禁止类型（ENUM/SET）、禁止时间函数、禁止项（外键/视图/触发器/存储过程）、禁止预留字段、COMMENT非空、索引数量、索引命名、字符集。

**结果处理**：

- **FAIL**（Critical 级别）→ 必须修正，重新运行直到无 FAIL
- **团队规范偏差**：如果团队规范明确覆盖了某条规则（如 `is_deleted` 代替 `deleted_flag`、`delete_time` 代替 `deleted_time`、雪花biz_key代替AUTO_INCREMENT），在 db.md "规范偏差说明" 表中记录后可忽略对应报错
- **WARN**（Warning 级别）→ 逐条评估，合理理由可保留并在 db.md 中说明
- **PASS** → 进入 Step 6

脚本报告中的 FAIL 项，除非有明确的团队规范偏差记录，否则禁止跳过。

## 历史数据兼容方案 Brainstorming 规范

> 本规范在 `arch-design` skill 的"第二：数据库设计"中被调用。

### 核心原则

**历史数据兼容方案的制定不允许由 AI 自行决定，必须通过 Brainstorming 影响分析 + 用户确认流程。**

原因：数据库变更对存量数据的影响往往难以仅通过代码分析准确评估。数据分布特征（空值比例、数据量级、业务语义依赖）只有产品/业务方最清楚。AI 负责枚举变更影响和候选方案，用户负责决策。

### 触发条件

当需求涉及以下数据库变更时，**必须**执行历史数据兼容 Brainstorming：

| 触发条件                       | 示例                                                                      |
| ------------------------------ | ------------------------------------------------------------------------- |
| 对现有表新增 NOT NULL 字段     | 新增 `approval_status` NOT NULL DEFAULT 0，需确认存量数据默认值是否合理 |
| 修改现有字段类型或约束         | `VARCHAR(50)` → `VARCHAR(200)`、新增 UNIQUE 约束                     |
| 字段语义变更                   | `status` 字段枚举值增加/修改，存量数据含义变化                          |
| 新增表需从旧表迁移数据         | 拆分 `t_order` 为 `t_order_main` + `t_order_detail`                 |
| 新增字段与现有字段存在数据依赖 | 新增 `total_amount` 需要从明细表汇总回填                                |
| 删除或废弃现有字段             | 需确认是否有下游依赖，是否需要保留数据备份                                |

以下场景**不需要**历史数据兼容 Brainstorming：

- 纯新增独立表（无存量数据依赖）
- 仅新增可空字段（NULL ALLOWED，无默认值要求）
- 纯前端需求，无数据库变更
- 新增独立的查询接口，不修改现有表结构

### Brainstorming 流程

#### Step 1: 渐进式扫描受影响的数据库表结构（AI 执行）

1. 读取 `table_index.json` 定位需求涉及的表
2. 逐个加载对应 DDL 文件，获取完整的字段定义
3. 结合 sql-design-spec.md 公司规范，标注当前表结构与规范的差异
4. 识别所有需要变更的字段和变更类型

#### Step 2: 枚举变更影响分析（AI 执行，不跳过任何变更项）

对每张受影响的表，列出所有变更项及影响分析：

**变更类型分类：**

| 变更类型                 | 影响分析要点                                              |
| ------------------------ | --------------------------------------------------------- |
| 新增可空字段             | 存量数据为 NULL 是否影响业务逻辑？查询是否需要 COALESCE？ |
| 新增 NOT NULL 字段       | 默认值是否合理？是否需要回填历史数据？回填规则是什么？    |
| 修改字段类型（兼容）     | 如 VARCHAR 扩长度，是否影响索引？是否需要重建索引？       |
| 修改字段类型（不兼容）   | 如 INT → VARCHAR，存量数据如何转换？是否有数据丢失风险？ |
| 新增约束（UNIQUE/INDEX） | 存量数据是否有重复值？是否需要先清洗重复数据？            |
| 字段语义变更             | 存量数据中该字段的值在新语义下是否仍然有效？              |
| 删除字段                 | 是否有代码/查询/报表依赖该字段？是否需要数据备份？        |

**数据风险等级评估：**

| 风险等级 | 触发条件                                 | 必须采取的措施                           |
| -------- | ---------------------------------------- | ---------------------------------------- |
| 低风险   | 仅新增可空字段、新增独立表、兼容类型扩展 | 记录变更即可，无需特殊兼容               |
| 中风险   | NOT NULL 回填、兼容类型变更、新增索引    | 必须有回填脚本和验证方案                 |
| 高风险   | 不兼容类型变更、数据语义变更、跨表迁移   | 必须有完整迁移方案 + 回滚方案 + 灰度策略 |

#### Step 3: 呈现变更影响 + 候选兼容方案供用户确认

以结构化格式呈现，**禁止自行决定最终方案**，必须等用户确认：

```
## 数据库变更影响分析

### 受影响表 1：`t_xxx_info`（来源：`sql_ddl/{schema}.t_xxx_info.md`）

**当前关键字段：**
| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| existing_field | VARCHAR(50) | NOT NULL | 现有字段说明 |

**变更清单：**

| 变更类型 | 字段 | 变更内容 | 数据风险 |
|---------|------|---------|---------|
| 新增字段 | new_field | VARCHAR(100) NOT NULL DEFAULT '' | 中风险（需确认默认值） |
| 修改字段 | old_field | INT → BIGINT | 低风险（兼容扩展） |

### 候选兼容方案

| # | 方案 | 说明 | 优点 | 缺点 |
|---|------|------|------|------|
| A | DDL先行 + 数据回填 | 先执行DDL（带默认值），再异步回填 | 安全可控，分步验证 | 需维护回填脚本 |
| B | 影子表迁移 | 建新表 → 迁移数据 → 原子切名 | 零停机，可回滚 | 实现复杂 |
| C | 无需兼容 | 变更不影响存量数据 | 最简单 | 仅适用低风险 |

**风险等级评估：** {低/中/高}风险
**推荐：** {方案编号}（理由：{具体原因}）

请确认选择哪个兼容方案（回复编号，如 "A" 或 "仅C"）：
```

#### Step 4: 用户确认后锁定兼容方案

- 用户确认后，将选定方案记录为最终数据兼容方案
- 完整兼容方案输出到 `$WORK_DIR/design/db/data-cleaning-plan.md`
- 兼容方案必须包含：
  - DDL 变更说明（新增/修改的字段、类型、约束）
  - 数据回填/迁移策略（范围、规则、执行时机、预估耗时）
  - 验证方案（如何确认回填/迁移完成且数据正确）
  - 回滚方案（执行失败时的降级策略）

### 常见错误警示

| 错误模式           | 示例                                     | Brainstorming 如何避免          |
| ------------------ | ---------------------------------------- | ------------------------------- |
| 忽略存量数据默认值 | 新增 NOT NULL 字段未设默认值导致写入失败 | 列出所有变更项并标注风险等级    |
| 低估数据量         | 回填百万级数据未考虑分批执行             | 评估影响范围时考虑数据量级      |
