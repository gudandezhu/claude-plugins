# 任务拆分评审 Rubric

总分 100 分，**≥ 90 分通过，< 90 分不通过**。每个检查项按三级评分：通过（满分）、部分通过（50%）、不通过（0 分）。部分通过适用于：内容存在但不够完整/精确，而非完全缺失。

## 维度汇总

| 维度 | 满分 |
|------|------|
| 完整性 | 25 |
| 粒度 | 10 |
| 依赖 | 20 |
| 可构建性 | 20 |
| DDL字段 | 5 |
| 内容质量 | 15 |
| 迭代覆盖 | 5 |
| **合计** | **100** |

---

## 完整性（满分 25）

对照 `design/tech-design.md` 验证任务覆盖度。读取每个迭代的 `task-list.json` 和任务详情文档。

- [5分] tech-design.md 中所有接口是否都有对应的后端任务
- [5分] tech-design.md 中所有页面是否都有对应的前端任务
- [5分] tech-design.md 中所有异常场景是否在任务详情中被覆盖
- [5分] task-list.json 的 tasks 数组长度是否与实际任务详情文档数量一致
- [5分] 每个任务的 frontmatter `acceptance-criteria` 字段至少包含一个 AC-XX 或 UI-XX 引用（无 AC 可分配的任务需在正文中说明原因）

## 粒度（满分 10）

检查每个任务的大小是否适合 Agent 单 session 完成且充分利用会话容量。

- [4分] 每个任务是否可在 Agent 单 session 内完成（不超出 context window），且不存在极小任务（信号：INFRA 任务仅含一个只被一个 BE 使用的 DTO 定义；BE 任务仅含单一简单 CRUD 接口；FE 公共组件仅被一个页面使用）
- [3分] 是否存在过大的任务需要进一步拆分（信号：单任务包含超过 3 个不同业务子域，或核心流程描述超过 20 个步骤）
- [3分] 是否存在过小的任务可以合并（信号：同一实体的 CRUD 接口被拆成多个独立 BE 任务；DTO 定义独立成 INFRA 但只被一个 BE 使用；公共组件独立成 FE 但只被一个页面使用）

## 依赖（满分 20）

验证依赖关系图和任务排序。

- [6分] 依赖关系是否构成有向无环图（无循环依赖）
- [3分] 基础设施任务（INFRA）是否排在最前
- [3分] phases 是否按拓扑排序分层（INFRA 在前，BE/FE 可同层并行）
- [5分] 跨迭代依赖标注是否与实际迭代顺序一致
- [3分] 每个任务的"依赖任务"字段是否已填写（无依赖填"无"，不允许留空）

## 可构建性（满分 20）

验证每个迭代可独立构建和验证。

- [6分] 每个迭代是否包含前后端闭环（可独立验证）
- [4分] 验收标准是否按4个阶段（开发/自测/联调/QA）组织
- [5分] 验收标准每条是否可被 Agent 自动判定通过/失败（不允许模糊描述如"功能正常"）
- [5分] 任务间的接口契约是否一致（前端任务引用的 API 路径与后端任务定义的路径是否匹配）

## DDL 字段校验（满分 5）

检查任务中引用的数据库字段在 DDL 中是否存在。通过 `$JLC_AI_WORKSPACE/biz-tech-docs/INDEX.md` 路由表定位 DDL 文件。

- [3分] SQL 骨架、VO/BO 字段映射、WHERE 条件中引用的字段是否在 DDL 中实际存在
- [1分] SQL 脚本（`tasks/sql/`）中引用的表名和字段名是否与 DDL 一致
- [1分] 不存在的字段是否已在任务"前置确认项"中标注为阻塞项（而非直接使用）

## 内容质量（满分 15）

检查每个任务详情文档的内容质量。

- [4分] 后端任务是否包含业务逻辑伪代码（不是具体 Java 代码）
- [4分] 任务详情中是否存在占位符（`{request-body}`、`/api_url`、"类似TaskN"、"同上"等）
- [4分] 每条交互操作、异常分支是否可溯源至 tech-design.md 或 PRD
- [3分] curl 验证命令是否使用真实路径和参数（不允许占位符）

## 迭代覆盖（满分 5）

验证所有功能模块都已归属到迭代。

- [3分] tech-design.md 中所有页面/功能模块是否都归属到某个迭代，无遗漏
- [2分] 迭代规划是否与 tech-design.md 第7章的迭代规划一致（如不一致需说明原因）

---

## 评审校准

- 扣分项必须附上具体的问题位置和改进建议
- 单个高权重检查项失分（如循环依赖 -6 分、接口遗漏 -5 分）往往直接导致不通过
- **≥ 90 分通过，< 90 分不通过**

## 完成前验证

在输出评审结论前，必须自我验证：
- [ ] 是否亲自读取了每个迭代的 task-list.json？
- [ ] 是否抽查了至少每个角色（BE/FE/INFRA/TS）各一个任务详情文档？
- [ ] 是否对照 tech-design.md 验证了接口和页面的覆盖度？
- [ ] 是否检查了至少一个前端任务引用的 API 路径与对应后端任务/API文档的一致性？
- [ ] 标记的问题是否都附带了具体的位置和改进建议？
