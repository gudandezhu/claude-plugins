# 代码审查 Rubric

总分 100 分，**≥ 90 分通过，< 90 分不通过**。每个检查项按三级评分：通过（满分）、部分通过（50%）、不通过（0 分）。部分通过适用于：内容存在但不够完整/精确，而非完全缺失。

## 前置准备

目标内容为项目源码。通过 Glob + Read 读取目标目录下的源码文件（排除 `target/`、`node_modules/`、`.git/` 等构建产物）。

从任务文件 frontmatter 获取审查上下文：
- `acceptance-criteria`：AC 条目 → 需求合规检查
- `api-docs`：API 文档路径 → 接口合规检查
- `tech-design-sections`：技术设计章节 → 实现方案对照

## 维度汇总

| 维度 | 满分 |
|------|------|
| 需求合规 | 40 |
| 代码质量 | 60 |
| **合计** | **100** |

---

## 需求合规（满分 40）

逐条对照任务描述检查代码实现。**不要信任开发者自述，必须读代码验证。**

- [10分] 是否实现了任务要求的所有功能
- [8分] 有没有遗漏的需求点
- [8分] 有没有多做了需求之外的东西
- [7分] 对需求的理解是否正确（有没有偏差）
- [7分] 边界情况和异常场景是否覆盖

## 代码质量（满分 60）

对变更代码进行质量审查。

- [10分] 职责分离是否清晰（每个文件/类/方法只做一件事）
- [10分] 错误处理是否完善（异常和边界情况覆盖）
- [8分] 是否遵循项目现有的编码风格和模式
- [8分] 测试是否覆盖核心逻辑（测真实行为而非 mock）
- [8分] 有没有安全隐患（XSS、SQL注入、敏感信息泄露）
- [8分] 有没有明显的性能问题
- [4分] DRY 原则：有没有重复代码
- [4分] YAGNI 原则：有没有不需要的功能

---

## 评审校准

- 不读代码就评分 → 自动不通过
- 每个问题必须包含 file:line 引用、问题描述、修复建议
- 按严重程度分类：Critical（必须修复）> Important（应该修复）> Minor（建议优化）
- **≥ 90 分通过，< 90 分不通过**

## 完成前验证

在输出评审结论前，必须自我验证：
- [ ] 是否读取了实际代码（不是只看 diff 摘要）？
- [ ] 是否按严重程度分类了所有问题？
- [ ] 每个问题是否都有 file:line 引用？
- [ ] 是否说明了问题的原因和影响？
