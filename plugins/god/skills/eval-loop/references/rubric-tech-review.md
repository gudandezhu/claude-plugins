# 技术方案评审 Rubric

总分 100 分，**≥ 90 分通过，< 90 分不通过**。每个检查项按三级评分：通过（满分）、部分通过（50%）、不通过（0 分）。部分通过适用于：内容存在但不够完整/精确，而非完全缺失。

## 前置准备

按三级优先级加载技术规范作为评审判据：**项目规范 > 团队规范 > 公司规范**。

| 层级 | 路径（相对 `$JLC_AI_WORKSPACE`） | 用途 |
|------|------|------|
| 公司 | `tech-specs/api-spec/api-spec.md` | API 接口规范 |
| 公司 | `tech-specs/sql-spec/sql-design-spec.md` | 数据库设计规范 |
| 公司 | `tech-specs/review-spec/solution-review-spec.md` | 方案评审标准 |
| 团队 | `biz-tech-docs/` | 团队技术知识库 |
| 团队 | `biz-product-docs/` | 团队产品文档 |
| 项目 | `projects/{project}/CLAUDE.md` | 项目架构约束 |

不存在的层级跳过，不报错。

## 维度汇总

| 维度 | 满分 |
|------|------|
| 完整性 | 30 |
| 合理性 | 25 |
| 深度 | 15 |
| 规范性 | 10 |
| 规范符合性 | 20 |
| **合计** | **100** |

---

## 完整性（满分 30）

逐章节读取方案文档，验证所有必要内容是否存在。

- [5分] 是否分析了现有代码基础（各层完成状态）
- [3分] 是否明确了涉及的微服务及代码库路径
- [3分] 是否列出了 API 接口总览表（接口名、方法、路径、所属服务、说明）
- [3分] API 接口总览表是否覆盖了所有需求功能点对应的接口
- [3分] 是否描述了核心业务处理流程
- [3分] 是否包含领域模型定义
- [2分] 是否标注了跨服务调用链路
- [3分] 是否列出了后端架构分层设计和跨模块数据获取映射表
- [1分] 是否列出了新增文件清单
- [2分] 涉及前端时，是否包含前端架构章节（路由、组件结构、差异化策略）
- [2分] 涉及数据校验时，是否包含校验规则章节（校验项、规则、异常判定标准）

## 合理性（满分 25）

验证方案设计是否合理。

- [5分] 微服务划分是否合理，职责是否清晰
- [4分] 接口设计是否符合 RESTful 规范
- [4分] 异常场景是否有独立章节系统性覆盖（不只是散落在流程图分支中）
- [5分] 数据流转是否完整闭环
- [4分] 迭代规划是否前后端闭环（每个迭代可独立验证）
- [3分] 跨模块调用是否标注了具体 Service 类名

## 深度（满分 15）

验证内容是否有足够的实现细节。

- [5分] 核心处理流程是否同时包含流程图和实现描述段落（不只是流程图）
- [5分] 实现描述是否标注了关键 Service 调用链和跨模块调用点
- [5分] 数据校验规则是否有明确的异常判定标准（如阈值、条件）

## 规范性（满分 10）

验证文档格式和内容规范。

- [5分] 方案中是否包含具体代码（不允许，业务逻辑伪代码除外）— 包含具体代码则此项 0 分
- [5分] 文档结构是否清晰可读（章节层次、列表格式、命名风格统一）

## 规范符合性（满分 20）

基于前置准备中加载的规范逐条对照。

- [5分] 接口设计是否符合 API 接口规范（三级优先级取最高）
- [4分] 数据库设计是否符合数据库设计规���（字段、索引、命名、必备字段）
- [3分] 去重结论是否与数据库表索引一致
- [3分] 复用接口是否在代码中真实存在（Grep Controller 确认路径/方法名/Controller 均匹配）
- [3分] 方案是否满足方案评审标准的通过条件
- [2分] 项目特定约束（如 CLAUDE.md 中的架构约定）是否被遵守

---

## 评审校准

- 不信任作者自述，必须独立验证每个检查项
- 扣分项必须附上具体章节位置和改进建议
- 单个高权重检查项失分（如接口遗漏 -5 分、数据流断裂 -5 分）往往直接导致不通过
- **≥ 90 分通过，< 90 分不通过**

## 完成前验证

在输出评审结论前，必须自我验证：
- [ ] 是否亲自读取了方案文档的每个章节？（不是只看目录）
- [ ] 是否独立验证了每个检查项？（不是信任作者声明）
- [ ] 标记的问题是否都附带了具体的位置和改进建议？
- [ ] 是否加载了相关技术规范作为判据？
