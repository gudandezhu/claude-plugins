# 产品需求 Specs 工作流程

## 设计系统配置

> **当前激活的设计系统：`dayu`**
>
> 配置文件路径：`rules/design-systems/{system-name}/`
> - `component-map.md` — 组件ID映射（语义名称 → 具体组件ID）
> - `design-tokens.md` — 设计Token（颜色/字体/间距/尺寸）
> - `design-rules.md` — 页面样式强制规范
>
> **切换设计系统**：修改上方系统名称（如改为 `antd`），工作流自动加载对应配置。
> 可用设计系统：`dayu`（大禹平台）、`antd`（Ant Design，模板待填充）

## 概述

本文档定义了产品需求分析和设计的完整工作流程，采用**模块化迭代式**方法，确保每一步都在正确方向上。

## 核心原则

- **模块化迭代**：每个模块完成后等待用户确认，确保方向正确
- **质量保证**：通过强制自审确保文档质量
- **方向可控**：及时发现问题，避免大规模返工
- **渐进加载**：按阶段加载 Agent prompt，减少 context 占用
- **经验驱动**：从历史项目自审中提取经验，注入当前工作流

## 执行模式

### 自动编排模式（`/prd-auto`，推荐）

使用 Lead PRD Agent 自动编排完整流程：
- 自动检测 `需求/active/{module}/{slug}/` 目录文件判断当前阶段
- 按需加载对应 Phase 文件（而非完整 Agent prompt）
- 阶段间通过 Context Snapshot 传递上下文摘要
- 支持并行调度（ER图+用例图、验证+自审）
- 自动注入经验记忆库提醒
- 支持中断恢复（新会话说"继续 {slug} 项目"）

详见：`commands/prd.md` + `skills/prd/phases/prd-phase-writing.md`

### 手动模式（`/prd`、`/prd-dayu`）

直接激活特定 Agent，适合单阶段修改或调试。用 `#agent-name` 关键词切换。
两种模式产出文件格式一致，可随时互切。

## Context Snapshot 机制

每个阶段完成后自动更新 `需求/active/{module}/{slug}/05-context-snapshot.md`，作为阶段间上下文传递载体：

- **模板**：`${CLAUDE_PLUGIN_ROOT}/skills/prd/templates/context-snapshot.md`
- **内容**：需求摘要、功能架构摘要、PRD编写摘要、原型设计摘要、验证摘要、自审摘要、阶段流转记录
- **规则**：下一阶段的 sub-agent 只读 snapshot + 当前阶段直接输入文件，不回溯全部历史
- **协作**：每个 Agent/Phase 文件都有「Context Snapshot 协作」区块，明确读取和更新规则

## 并行执行

以下阶段可以并行调度：

**并行组A（阶段3+4）**：ER图 + 用例图
- 两者都只依赖 01 和 02 文件，无互相依赖
- Lead Agent 同时发出两个 sub-agent，完成后汇总更新 snapshot

**并行组B（阶段7验证+8）**：原型验证 + 需求自审
- 原型验证关注视觉交互，需求自审关注文档逻辑，检查维度不同
- 两者都完成后 Lead Agent 汇总判断：都通过→完成，任一不通过→回退

>
> **所有PRD项目必须在 `需求/active/{module}/` 目录下创建**，模块名与 `wiki/modules/` 对齐
>
> **正确的项目路径**：
> - ✅ 正确：`需求/active/monitoring/alarm-escalation/`
> - ✅ 正确：`需求/active/code-repository/code-repository-management/`

> - ❌ 错误：`alarm-escalation/`（不能在根目录）
>
> **可用模块**（与 wiki/modules/ 一一对应）：
> - `monitoring` — 监控告警
> - `code-repository` — 代码仓库
> - `security` — 安全凭据
> - `frontend-monitoring` — 前端监控
> - `approval-workflow` — 审批流程
> - `dayu-platform` — 大禹平台
> - `gateway` — 网关
> - `apim` — API管理
>
> **新增模块**：如果需求不属于已有模块，可新建模块目录，同时在 `wiki/modules/` 下同步创建对应目录。
>
> **命名规则**：
> - 模块目录和项目文件夹均使用kebab-case（小写+连字符）
> - 只使用英文字母、数字、连字符
> - 不使用中文、空格、特殊字符

> **🚨 文件命名规范（强制）**：
>
> **必须使用英文文件名**，禁止使用中文文件名
>
> **原因**：
> - 中文文件名在不同操作系统、工具间存在编码转换问题
> - Windows文件系统、Bash、Git对中文文件名支持不一致
> - 影响跨平台协作和版本控制
>
> **命名规则**：
> - 只使用英文字母、数字、连字符（-）、下划线（_）
> - 不使用中文、特殊字符、空格
> - 使用kebab-case（小写+连字符）
>
> **示例**：
> - ✅ 正确：`01-requirements-analysis.md`
> - ✅ 正确：`07-prototype/prototype-test-report.md`
> - ❌ 错误：`01-需求分析.md`
> - ❌ 错误：`06-原型自测报告.md`

## 核心阶段

### 阶段1：需求分析（01-requirements-analysis.md）

**目标**：深入理解需求本质和价值

**AI助手角色**：资深产品设计顾问，具备用户需求洞察、商业分析、竞品分析等能力

**模块化执行**：每个模块完成后等待用户确认

#### 模块1.1：需求背景与目标
- 当前问题和业务现状
- 核心目标和成功标准
- 业务价值和用户价值

#### 模块1.2：用户角色与场景
- 目标用户角色定义
- 主要使用场景描述
- 用户旅程和痛点分析

#### 模块1.3：策略分析
- 竞品分析和市场定位
- 产品策略和功能优先级
- 风险识别和机会评估

#### 模块1.3.5：需求挑战（模块1.2完成后执行）
- **问题 vs 方案**：用户描述的是真正的问题，还是已经预设了解决方案？
- **范围合理性**：需求范围是否过大（应该拆期）或过小（遗漏关键场景）？
- **用户真实诉求**：用户说的和用户真正需要的是否一致？
- 挑战结论写入 01-requirements-analysis.md 的「需求挑战记录」章节
- 如需调整则回到模块1.1更新，确认维持则继续

#### 模块1.4：已有平台能力盘点
- **目标**：避免重复建设，优先复用已有平台能力
- **前置步骤**（⚠️ 强制）：
  1. 先读取 `大禹平台产品知识库.md` 了解平台全貌和完整导航结构
  2. 根据需求描述，定位涉及的模块目录，读取 `大禹平台产品知识库/` 下对应模块的概述文档
  3. 当需求涉及具体页面改造或关联时，深入读取对应子页面文档，获取现有字段、筛选条件、操作按钮、数据量等信息
- **盘点内容**：
  - 已有的通用服务（告警通知、权限管理、审计日志、消息推送等）
  - 已有的数据源（CMDB、监控系统、日志系统、链路追踪等）
  - 已有的组件/SDK（认证SDK、文件上传、导出服务等）
  - 已有的关联页面（知识库中与本需求相关的现有页面和功能）
- **输出**：
  | 能力类型 | 已有平台能力 | 本需求是否需要 | 对接方式 |
  |---------|------------|--------------|---------|
  | 告警通知 | 已有告警平台 | 是 | API对接，推送事件 |
  | 权限管理 | 平台权限系统 | 是 | 直接复用 |
  | 审计日志 | 通用审计服务 | 是 | 事件上报 |
  | ... | ... | ... | ... |
- **原则**：能复用的不自建，需要对接的在 PRD 关联性需求中说明

**主动提问机制**：当需求点不明确时，AI助手必须主动提问澄清，不能基于假设进行分析。

#### 需求完整性检查清单（阶段1完成前必须通过）⚠️ 强制

> 需求录入的完整性直接决定后续输出质量。以下清单必须在进入阶段2前全部确认。

| 检查项 | 必须包含 | 通过 |
|--------|---------|------|
| 业务背景 | 为什么做、当前痛点、期望效果 | ✅/❌ |
| 用户角色 | 所有角色定义、数量、核心诉求 | ✅/❌ |
| 核心业务流程 | 主要操作流程（至少文字描述） | ✅/❌ |
| 数据实体 | 核心业务对象和关系（至少口头确认） | ✅/❌ |
| 已有平台能力 | 可复用的服务/系统/组件盘点 | ✅/❌ |
| 非功能需求 | 性能/安全/兼容性基本要求 | ✅/❌ |
| 需求边界 | 明确做什么、不做什么 | ✅/❌ |

**不完整的需求不允许进入阶段2**。如有缺失项，AI 助手必须主动提问补全。

### 阶段2：功能范围脑图（02-feature-scope.mm）

**目标**：明确功能边界，梳理功能结构

**前置步骤：范围决策**（在拆功能前执行）
- 基于需求分析结果，向用户确认范围策略：完整实现 / 核心优先 / 最小可用 / 按需裁剪
- 范围决策写入 02-feature-scope.mm 对应节点
- 必须等用户确认后才开始拆功能

**格式要求**：
- **FreeMind格式**（.mm）：可用 XMind 打开查看和编辑

**模块化执行**：每个模块完成后等待用户确认

#### 模块2.1：功能架构
- 核心功能模块划分
- 每个模块的子功能分解
- 功能模块间的依赖关系

**输出格式**：
- FreeMind .mm 格式思维导图

**FreeMind .mm 格式说明**：
- XML 格式，以 `<map>` 为根元素
- 每个节点用 `<node TEXT="节点名称">` 表示
- 子节点嵌套在父节点内
- 可用 XMind 直接打开查看和编辑
- 示例结构见 feature-architect-agent.md

#### 模块2.2：非功能需求
- 性能需求（响应时间、并发量）
- 安全需求（权限控制、数据加密）
- 监控需求（接口监控、报警机制）
- 兼容性需求（浏览器、设备支持）

**非功能需求同样以 FreeMind .mm 格式输出**，作为 02-feature-scope.mm 的子节点。

#### 模块2.3：技术实现与关联影响
- 技术架构建议和实现难度评估
- 涉及的系统和集成点
- 对现有系统的影响分析

### 阶段3：产品模块ER关系图（04a-er-diagram.drawio）

**目标**：梳理数据模型及其关系

**AI助手角色**：资深IT产品经理 + 数据建模专家

**模块化执行**：每个模块完成后等待用户确认

#### 模块3.1：实体识别

#### 模块3.2：关系定义

#### 模块3.3：字段详细说明
- 每个实体的字段定义
- 字段名称、类型、长度、规则
- 字段详细说明以表格形式写入 `.drawio` 文件的备注区域或单独页面

### 阶段4：用户用例全景图（04b-use-cases.drawio）

**目标**：梳理不同角色如何使用产品功能

**AI助手角色**：资深IT产品经理 + 用户体验专家

**模块化执行**：每个模块完成后等待用户确认

#### 模块4.1：用户角色定义
- 列出所有用户角色（如管理员、普通用户、访客）
- 说明每个角色的权限范围

#### 模块4.2：用例场景梳理
- 每个角色的主要使用场景
- 场景的前置条件和后置条件

**重要说明 - 用例图 vs 流程图**：

> **⚠️ 关键区别**：
>
> **1. 用例图（Use Case Diagram）- 核心输出，必须包含**
> - **目的**：展示**参与者和用例的关系**
> - **包含元素**：
>   - 参与者：用火柴人图标表示
>   - 用例：用椭圆表示
>   - 系统边界：用矩形框表示
>   - 关系：关联（实线）、包含（<<include>>虚线）、扩展（<<extend>>虚线）
>
> **2. 业务流程图（Business Process Flow）- 可选输出**
> - **目的**：展示**操作步骤的执行顺序**
> - **包含元素**：
>   - 开始/结束节点（圆角矩形）
>   - 处理步骤（矩形）
>   - 判断节点（菱形）
> - **何时使用**：当流程复杂时，详细说明步骤

**输出格式**：Draw.io 文件（`.drawio`，可用 VS Code Draw.io 插件直接查看和编辑）

- 用例图和业务流程图统一放在同一个 `.drawio` 文件中，使用多页面（Page）区分
- Page 1：用例图
- Page 2：业务流程图（可选）

#### 模块4.3：角色-功能矩阵
- 哪些角色可以使用哪些功能
- 功能与角色的对应关系
- 角色-功能矩阵以表格形式写入 `.drawio` 文件的单独页面

### 阶段2与阶段6的边界说明

**阶段2：功能范围脑图**（宏观层面）
- **目的**：梳理功能边界和模块关系
- **产出**：树状结构的功能分解
- **粒度**：功能模块级别，不涉及具体细节
- **关注点**：有什么功能、如何分组、依赖关系

**阶段3：产品模块ER关系图**（数据模型层面）
- **目的**：梳理数据模型及其关系
- **产出**：实体关系图和字段定义
- **粒度**：实体和字段级别
- **关注点**：有哪些实体、实体间关系、字段定义

**阶段4：用户用例全景图**（用户视角层面）
- **目的**：梳理不同角色如何使用产品功能
- **产出**：用例全景图和角色-功能矩阵
- **粒度**：用户角色和用例级别
- **关注点**：谁在什么场景下使用什么功能

**阶段6：产品需求文档**（微观层面）
- **目的**：详细描述功能实现细节
- **产出**：包含字段、交互、校验的完整文档
- **粒度**：字段级别，包含所有细节
- **关注点**：具体怎么做、每个字段的规则、每个交互的细节

**明确区分原则**：

| 对比维度 | 阶段2（功能范围） | 阶段3（ER关系图） | 阶段4（用例全景图） | 阶段6（PRD） |
|---------|-----------------|-----------------|-------------------|-------------|
| **示例** | 用户管理 | 用户实体、订单实体 | 普通用户查看订单 | 用户列表页字段表格 |
| **粒度** | 功能模块 | 实体和字段 | 用户角色和用例 | 字段级别 |
| **内容** | 用户列表、用户详情 | 用户、订单、商品 | 角色权限矩阵 | 字段名称、类型、长度、校验规则 |
| **格式** | 树状结构 | 表格+文字描述 |
| **深度** | 2-3层分解 | 每个字段的完整定义 |

**示例对比**：

❌ **阶段2不应该写**：
```markdown
## 用户列表
- 用户ID（string，系统唯一标识，最大50字符）
- 用户名（string，最大20字符，必填）
```
→ 这太详细了，应该在阶段3

✅ **阶段2应该写**：
```markdown
## 1. 用户管理
### 1.1 用户列表
- 用户信息展示
- 用户搜索
- 用户操作

### 1.2 用户详情
- 用户基本信息
- 用户权限信息
- 用户操作历史
```

> 从历史项目经验看，一次生成很难产出完美原型——5/10 项目出现"原型与 PRD 不一致"，主要原因是一轮生成时同时关注结构、内容、精度、一致性，容易顾此失彼。
> **加载 skill `prototype-iterate`**，按其 5 轮迭代模型执行：结构骨架验证 → 内容填充与精度 → 打磨与一致性 → PRD覆盖度核对 → 最终验收与导出。
> 每轮关注点分层，逐步提升原型质量。详细检查项和操作步骤遵循 `prototype-iterate` 定义。

**3 轮迭代模型**：

```
第1轮：结构骨架（所有页面）
  → 重点：页面结构、组件布局、侧边栏/面包屑导航

  → 不纠结细节，先把所有页面框架搭出来

  → 验证：snapshot_layout 对齐验证 + PRD 字段核对
  → 解决"原型与 PRD 不一致"问题
      ↓
第3轮：打磨与一致性（全局检查）
  → 重点：跨页面一致性、弹窗/表单补全、操作闭环
  → 验证：完整 6 维度打分（步骤5）
  → 确保所有页面风格统一、操作链路完整
```

**操作**：对每个页面执行以下操作：

```
  - 列表页加载状态（骨架屏）
  - 列表页空状态
  - 操作成功/失败消息提示
  - 首次使用引导（仪表盘类页面）
  - 无权限操作状态
```

**第3轮验证**（全局检查）：
- 使用 `get_screenshot()` 截取所有页面
- 检查项（聚焦一致性和完整性）：
  - [ ] 所有页面侧边栏菜单一致
  - [ ] 所有弹窗已补全（对照 PRD 操作定义）
  - [ ] 操作闭环完整（每个操作入口有对应目标）
  - [ ] 卡片样式完整（R() 替换后保留 fill/cornerRadius/padding/stroke）
  - [ ] 无视觉不一致（颜色、字体、间距）
- 第3轮验证通过后，进入步骤5正式验证

> **⚠️ 迭代规则**：
> - 3 轮迭代是标准流程，每轮关注点不同，不可跳过
> - 每轮验证发现的问题必须在当轮修复，不可推迟到下一轮
> - 如果第3轮验证仍有重大问题（结构性错误），可追加第4轮，但最多不超过4轮
> - 每轮验证结果记录到 07-prototype/prototype-test-report.md 的迭代记录区块

#### 步骤5：验证与自测（Validate）

> 合并了原型技术验证和功能自测，一次性完成所有检查。
> 详细指南：参见 `rules/prototype-self-test-guide.md`

**技术验证**：
1. **视觉验证**：使用 `get_screenshot()` 截取每个页面进行视觉检查
2. **表格对齐验证**：使用 `snapshot_layout()` 验证表头和数据行的 x 坐标和 width 一致（±2px）
3. **侧边栏一致性验证**：所有页面侧边栏菜单结构一致，当前页高亮正确
4. **卡片样式验证**：使用 R() 替换的节点是否保留了完整卡片样式（fill/cornerRadius/padding/stroke）
5. **设计规范验证**：对照 `rules/dayu-design-system.md` 第15章检查所有强制规范

**功能自测**：
6. **覆盖度检查**：原型是否覆盖所有功能清单
7. **操作闭环测试**：检查列表页每个操作（查看/编辑/删除）是否有对应的目标页面/弹窗
8. **界面元素检查**：所有元素可交互、有反馈
9. **用户体验检查**：可用性、一致性、视觉设计

**通过标准**：
- 6维度打分（功能覆盖、操作闭环、表格精度、设计规范、交互完整性、视觉一致性），每项0-10分
- 综合评分 ≥ 48/60（80%）且无单项 ≤ 4分 → 通过
- 功能覆盖率 ≥ 90%
- 操作闭环测试通过率 ≥ 85%
- 界面元素可交互率 ≥ 95%

**输出**：`07-prototype/prototype-test-report.md`

**不通过时**：修复问题 → 重新验证，直到通过。通过后才能进入阶段8。

> 由于初始化时已将组件库复制到 `需求/active/{module}/{slug}/07-prototype/prototype.pen` 并直接在该文件上设计，设计稿会自动保存到正确位置，无需额外复制。

1. 确认 .pen 文件已保存在 `需求/active/{module}/{slug}/07-prototype/prototype.pen`
2. 使用 `export_nodes()` 导出各页面为图片，保存到 `需求/active/{module}/{slug}/assets/` 目录（可选，便于 PRD 文档内嵌截图）

### 阶段7附：产品设计审查（推荐执行）

**目标**：从产品经理视角全面审查 PRD 和原型的设计质量，发现架构层面的问题

**触发条件**：原型自测通过后，进入文档自审前

**审查维度**：

#### 1. 功能完整性审查
- PRD 中定义的所有功能是否都有对应的原型页面
- 每个模块的 CRUD 是否完整（列表/表单/详情/删除）
- 页面关联是否闭环（操作入口 → 目标页面）

#### 2. 架构合理性审查
- 数据层级是否合理（是否有冗余层级可以合并）
- 已有平台能力是否充分复用（告警/权限/审计等）
- 功能边界是否清晰（自建 vs 对接）

#### 3. PRD 与原型一致性审查
- PRD 字段定义与原型展示是否一致
- PRD 新增的功能章节是否有对应原型
- 变更记录是否完整反映所有修改

#### 4. 设计规范一致性审查
- 所有页面是否遵循 `rules/dayu-design-system.md` 第15章规范
- 侧边栏菜单是否全局一致
- 表格对齐是否通过 snapshot_layout 验证
- 卡片样式是否完整（R()替换后）

**输出**：问题清单（按 P0/P1/P2 分级），逐项修复后进入阶段7.5或阶段8

### 阶段7.5：跨职能快速评审（按需）

**目标**：引入人类视角的结构化评审，弥补 AI 在业务判断、技术可行性、真实用户体验等维度的盲区

**触发条件**：
- 大型需求（10+人天）：必须执行
- 中型需求（4-10人天）：建议执行
- 小型需求（1-3人天）：可跳过

**执行方式**：参照 `rules/cross-functional-review-guide.md`

**输入**：06-prd.md + 07-prototype/prototype.pen + 08-self-review.md

**评审角色**：
- 产品视角（5项）：需求目标、用户场景、业务规则、优先级、验收标准
- 设计视角（5项）：交互一致性、信息架构、组件规范、异常状态、操作效率
- 研发视角（5项）：技术可行性、接口定义、性能风险、数据模型、关联影响
- 测试视角（3项）：可测试性、边界条件、回归范围

**输出**：评审意见（阻塞/建议/通过）

**流转规则**：
- 有阻塞问题 → 回到阶段6修改 PRD/原型，修改后重新进入阶段7验证
- 仅有建议问题 → 记录到 PRD 变更记录，进入阶段8
- 全部通过 → 进入阶段8

### 阶段7附：设计资产沉淀（推荐执行）

**目标**：将原型设计中产生的可复用组件和设计模式沉淀到设计系统中，避免重复造轮子

**触发条件**：原型设计完成且通过自测后

**检查清单**：

| 检查项 | 说明 | 是否需要沉淀 |
|--------|------|-------------|
| 新组件 | 原型中是否创建了组件库中不存在的通用组件（如统计卡片、可编辑表格行等） | ✅/❌ |
| 新交互模式 | 是否出现了新的交互模式（如批量操作弹窗、变更预览、执行进度等） | ✅/❌ |
| 新状态样式 | 是否定义了新的状态样式（如跳过状态的橙色卡片、NEW标签等） | ✅/❌ |

**沉淀方式**：

1. **新组件** → 添加到 `dayu_platform.lib.pen` 组件库，设置 `reusable: true`，更新 `rules/dayu-design-system.md` 第11章组件ID映射表
2. **新交互模式** → 更新 `rules/dayu-design-system.md` 对应章节，记录模式的结构、样式和适用场景
3. **新状态样式** → 更新 `rules/dayu-design-system.md` 颜色规范或状态徽章规范

> **原则**：如果一个组件或模式在未来其他需求中可能被复用，就应该沉淀。宁可多沉淀，不要遗漏。

## 阶段9：需求变更管理（按需执行）

**目标**：规范需求变更流程，确保变更可控、可追溯

**触发条件**：
- 需求文档提交审核后
- 开发过程中发现需求需要调整
- 业务需求发生变化
- 技术实现方案需要调整

### 变更类型

#### 变更类型分类

| 变更类型 | 说明 | 影响程度 | 审批要求 |
|---------|------|---------|---------|
| **新增功能** | 增加新的功能模块或子功能 | 高 | 需要重新评估规模和优先级 |
| **修改功能** | 修改已有功能的逻辑或实现 | 中/高 | 需要评估影响范围 |
| **删除功能** | 移除已有功能 | 中 | 需要确认删除必要性 |
| **优化调整** | 优化现有实现方案，不改变功能 | 低 | 可以快速审批 |
| **优先级调整** | 调整需求的开发顺序 | 低 | 需要重新排期 |

#### 步骤2：影响评估

**评估维度**：

| 评估维度 | 评估内容 | 评估方法 |
|---------|---------|---------|

| **开发影响** | 对已开发代码的影响 | 评估是否需要重构、返工 |
| **系统影响** | 对其他系统/模块的影响 | 分析依赖关系，评估影响范围 |

| **资源影响** | 对人力/时间成本的影响 | 评估是否需要增加资源 |

#### 步骤3：变更审批

**审批流程**：

1. **产品经理审核**
   - 确认变更必要性
   - 确认变更内容合理
   - 签字确认：_________

2. **技术负责人审核**（如涉及技术变更）
   - 评估技术可行性
   - 评估实现成本
   - 签字确认：_________

3. **业务方确认**（如涉及业务变更）
   - 确认业务需求变化
   - 确认优先级调整
   - 签字确认：_________

**快速通道**：
- 对于影响范围小的优化调整，可以简化审批流程
- 仅需产品经理确认即可

#### 步骤4：文档更新

**更新原则**：
1. **同步更新**：变更审批通过后，立即更新相关文档
2. **版本标记**：在文档中标记变更内容
3. **保持一致性**：确保01/02/03文档内容一致
4. **记录变更**：在变更日志中记录变更信息
5. **同步知识库**（⚠️ 强制）：PRD 变更涉及页面字段、功能模块、交互流程等变化时，必须同步更新 `大禹平台产品知识库/` 中受影响的模块文档，并在 `大禹平台产品知识库/CHANGELOG.md` 中记录变更

**更新方法**：

| 变更类型 | 更新方法 | 标记方式 |
|---------|---------|---------|
| 新增内容 | 在对应章节添加新内容 | 使用 ✅ NEW 标记 |
| 修改内容 | 直接修改原内容 | 使用 ⚠️ MODIFIED 标记 |
| 删除内容 | 删除或注释原内容 | 使用 ❌ DELETED 标记 |

**变更标记示例**：
```markdown
#### 模块3.3：功能描述

**列表页字段**：

| 字段名称 | 类型 | 说明 |
|---------|------|------|
| 用户ID | string | 系统唯一标识 |
| 用户名 | string | 用户注册时的用户名，最大20字符 |
| 手机号 | string | 脱敏显示，格式：138****1234 |
| 邮箱 | string | 用户邮箱地址 | ✅ NEW |
| 注册时间 | datetime | 格式：YYYY-MM-DD HH:mm:ss | ✅ NEW
```

### 变更管理原则

1. **及时性原则**：需求变更应在发现后立即申请，避免拖延
2. **完整性原则**：变更申请必须包含完整的变更内容和影响评估
3. **可追溯原则**：所有变更必须有记录，可追溯到变更人和变更原因
4. **审批原则**：变更必须经过审批，确保变更合理性和必要性
5. **文档同步原则**：变更审批通过后，立即更新相关文档

### 变更管理最佳实践

**建议**：
- ✅ 变更申请前先与相关方沟通，达成共识
- ✅ 小变更快速审批，大变更充分评估
- ✅ 定期回顾变更历史，总结经验教训
- ✅ 保持变更日志的完整性和准确性

**避免**：
- ❌ 频繁变更，造成团队疲劳
- ❌ 变更不记录，无法追溯
- ❌ 变更不更新文档，造成文档与实现不符
- ❌ 变更不评估影响，造成延期或返工
