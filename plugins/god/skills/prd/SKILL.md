# 产品经理知识库管理规则集

## 术语约定

| 术语 | 定义 |
|------|------|
| AC | 验收标准（Acceptance Criteria） |
| CTA | 行动号召（Call To Action） |

本 skill 分为核心层和适配层。核心层定义产出物契约和规则标准（不可覆盖）；适配层定义实现方式和流程参数（可通过项目 CLAUDE.md 覆盖）。

# PRD 核心方法论

以下是编写高质量 PRD 必须内化的方法论。每条包含定义、正例、反例、应用时机——正例是你要做到的标准，反例是你要避免的错误。

## 1. 信息架构先行

**定义**：写功能说明前，先定义核心数据实体及关系。实体模型是字段定义的根基，所有页面引用同一份实体定义。

**正例**：
```
先定义实体模型：
| 实体 | 核心字段 | 生命周期 | 来源 |
| 退货单 | 退货单号/状态/金额/原因 | 创建→审核→完成/拒绝 | 用户提交 |

再写功能页字段表时引用："退货单.状态"取值见实体模型定义。
```

**反例**：
```
列表页写"状态：待审核/已审核"，详情页写"状态：未处理/已处理"——同一字段两套值。
字段定义没有实体模型支撑，全凭各页面独立臆测。
```

**应用时机**：Phase 4 PRD 生成时，写模块5功能说明前

## 2. MECE 分解

**定义**：Mutually Exclusive, Collectively Exhaustive——功能清单不重叠、不遗漏。用角色 × 操作类型矩阵交叉校验。

**正例**：
```
| 角色 \ 操作 | 查看 | 创建 | 编辑 | 审批 | 导出 |
| 退货审核员 | ✅ 退货单列表 | ❌ 不适用（审核员不创建） | ✅ 批量标记 | ✅ 审核通过/拒绝 | ✅ 导出退货单 |
| 仓库人员 | ✅ 退货单列表（只读） | ❌ 不适用 | ❌ 不适用 | ❌ 不适用 | ❌ 不适用 |
```

**反例**：
```
功能清单只列了"退货单列表、批量标记、审核"——遗漏了"退货审核员需要导出"。
没有矩阵交叉检查，这种遗漏在评审前不会被发现。
```

**应用时机**：Phase 4 PRD 生成时，功能清单生成后做交叉校验

## 3. Given-When-Then 验收断言

**定义**：每条验收标准必须显式包含 Given（前置条件）、When（触发操作）、Then（预期结果）。没有 Given 的 AC 是模糊的，没有 Then 的 AC 不可判定。

**正例**：
```
| 编号 | Given（前置条件） | When（操作） | Then（预期结果） | 来源 |
| AC-FN-03 | 用户已登录且有退货审核权限，列表中存在≥2条待审核退货单 | 用户勾选多条退货单并点击"标记异常" | 所选退货单状态变更为"异常"，触发异常通知，列表刷新 | PRD 5.2 |
```

**反例**：
```
| 编号 | 前置条件 | 操作 | 预期结果 | 来源 |
| AC-FN-03 | - | 支持批量标记异常 | 标记成功 | PRD 5.2 |
问题：无 Given（不知道什么条件下操作）、Then 不可判定（"成功"是模糊词）。
```

**应用时机**：Phase 7 AC 提取时，AC-FN/AC-OP 每条必用

## 4. 用户故事驱动

**定义**：每个功能点必须能追溯到一条 User Story（As a [角色], I want [动作], so that [价值]）。没有"so that"的功能缺少存在理由。

**正例**：
```
As a 退货审核员, I want 批量勾选异常订单并一键标记, so that 每日从2小时审核压缩到15分钟
→ 功能"批量标记"关联此 User Story，开发理解价值，UI 优化方向明确（效率优先）
```

**反例**：
```
功能清单只写"批量标记" → 开发问"为什么要批量？一个一个点不行吗？"
没有 User Story 的功能是"老板要的"，不是"用户要的"。
```

**应用时机**：Phase 3 用户视角分析时产出 User Story，Phase 4 功能清单关联 User Story ID

## 5. 场景法（操作闭环）

**定义**：每个用户操作必须形成完整闭环——前置状态→触发操作→成功展示→失败处理→恢复方式→并发/批量场景。只有 happy path 的 PRD 上线后必有 bug。六要素缺一不可：

| 要素 | 含义 |
|------|------|
| 前置状态 | 操作前页面/数据处于什么状态 |
| 触发操作 | 用户做了什么（点击/输入/选择） |
| 成功展示 | 操作成功后页面变化、数据变化、反馈提示 |
| 失败处理 | 失败原因分类 + 各自的提示文案 + 页面停留状态 |
| 恢复方式 | 失败后用户如何重试/回滚/退出，数据是否保留 |
| 并发/批量 | 多次操作、批量操作、操作中途离开 |

**正例**：
```
"初始化仓库"操作闭环：
| 要素 | 描述 |
| 前置状态 | 仓库列表页，该仓库状态为"未初始化"，显示初始化按钮 |
| 触发操作 | 点击"初始化仓库"→ 二次确认弹窗 |
| 成功展示 | 按钮变为"已初始化"（置灰），页面刷新显示默认库位树，Toast"初始化成功" |
| 失败处理 | 网络超时：Toast"网络异常，请重试"，页面不变；数据冲突：Toast"该仓库已被初始化"，刷新页面 |
| 恢复方式 | 失败后可重新点击初始化按钮，不会产生脏数据 |
| 并发/批量 | 不可重复初始化（二次确认 + 后端幂等），批量初始化时逐条执行并显示进度 |
```

**反例**：
```
"初始化仓库"：
点击初始化 → 显示"操作成功"
→ 缺失：成功后页面什么状态？失败怎么办？重复点会怎样？初始化中断数据是否残留？
→ 开发自由发挥 → 上线后重复初始化导致数据重复、失败后无重试入口、用户不知道是否成功
```

**应用时机**：Phase 3 用户视角分析的关键操作流程，Phase 4 模块4业务流程和模块6异常场景

## 6. 状态机建模

**定义**：有状态的业务实体（≥3个状态）必须定义状态枚举表 + 合法流转路径。状态定义是业务逻辑，属于产品侧而非技术侧。

**正例**：
```
| 状态 | 含义 | 触发条件 | 可流转到 |
| 待审核 | 用户已提交，等待审核 | 用户提交退货申请 | 已审核/已拒绝 |
| 已审核 | 审核通过 | 审核员点击通过 | 已入库/已取消 |
| 已拒绝 | 审核不通过 | 审核员点击拒绝 | 终态（不可再操作） |
```

**反例**：
```
PRD 只在流程图里画了箭头。"已拒绝能不能重新提交？"→ 开发自己决定 → 线上行为和预期不一致。
```

**应用时机**：Phase 4 PRD 生成时，模块5功能说明中涉及有状态实体时

## 7. Kano 优先级分类

**定义**：功能分三类——基本型（没有=不可用）、期望型（越多越好）、兴奋型（惊喜，可延后）。scope 定义时区分优先级层次，所有功能标 P0 等于没有优先级。

**正例**：
```
| 功能 | Kano 分类 | 说明 |
| 退货单创建 | 基本型 | 没有=系统不可用 |
| 批量审核 | 期望型 | 效率提升，越多越好 |
| 智能异常识别 | 兴奋型 | 惊喜功能，可延后到 v2.0 |
```

**反例**：
```
所有功能都标 P0 → 开发周期爆炸 → 砍需求时没有判断依据 → 砍错了核心功能。
```

**应用时机**：Phase 2 brainstorm 的 Define Scope 步骤，Phase 4 模块11版本规划

## 8. 边界值与异常流

**定义**：四维度覆盖——数据异常 + 操作异常 + 权限异常 + 环境异常。每条含：触发条件→系统行为→提示文案→恢复方式。

**正例**：
```
| 异常类型 | 触发条件 | 系统行为 | 提示文案 | 恢复方式 |
| 数据异常 | 退货金额为负数 | 阻止提交，高亮字段 | "退货金额必须大于0" | 修正后重新提交 |
| 操作异常 | 5秒内重复点击提交 | 按钮置灰，防重复提交 | （无提示，静默防抖） | 5秒后按钮恢复 |
```

**反例**：
```
只写"需要异常处理"。没有触发条件、没有文案、没有恢复方式 → 开发自由发挥 → 上线后异常提示是"Error: null"。
```

**应用时机**：Phase 4 PRD 生成时，模块6异常与边界四维度覆盖

## 类型选择

zcode 内置多种 PRD 类型（平级），选一个使用。每个类型文件定义与核心层的差异规则（适用场景、模块要求、重点关注）。

```
skills/prd/types/
├── generic.md      # 通用 PRD（默认）
├── saas-erp.md     # SaaS ERP（多租户）
├── elmo.md         # Elmo 项目
├── dayu.md         # 大禹平台（含强制商业建模 + 知识库审计）
└── （维护者可新增更多类型）
```

类型文件可通过 frontmatter `modeling` 字段（`required` / `recommended` / `opt-in`）控制 Phase 3.5 商业建模阶段的激活。

根据 PRD 类型加载对应的类型文件。所有类型共享本文件的核心层（方法论、模块结构、硬性规则）和适配层（项目结构、模板机制、编码映射）。

## PRD 场景与模块库

PRD 不再使用固定的模块结构。根据需求场景，从模块库中动态选配。

### 场景识别（4类）

| 场景 | 特征 | 典型触发 |
|------|------|---------|
| **A. 新项目规划** | 从0到1，需要完整系统设计 | "搭建XX系统"、"新系统规划" |
| **B. 新增功能** | 现有系统增加新模块/新能力 | "新增XX功能"、"添加XX模块" |
| **C. 旧需求改造** | 修改已有功能的逻辑/规则/交互 | "优化XX流程"、"调整XX规则"、"改造XX" |
| **D. 子模块规范** | 大模块下的具体页面/功能细化 | "XX页面的详细设计"、"XX功能的字段规范" |

**识别规则**：
1. AI 从用户输入的关键词 + 上下文自动判断
2. 允许多选（混合需求取各场景模块集的并集）
3. 不确定时向用户展示候选方案，等待用户选择

**混合场景合并规则**：当场景多选时（如 B+C），取各场景模块集的并集。并集后同一模块可能来自不同场景——以主场景的语义为准（如 B+C 以 B 为主，M06 的改动类型标注以"新增"为主视角，"修改"为辅）。module-config.md 中标注每个模块的来源场景。

**类型×场景交互**：场景决定模块组合，类型决定模块内容增强。类型差异规则仅在被激活的模块上生效。

### 模块库（15个原子模块）

| ID | 模块 | 内容说明 | 达标要求 |
|---|------|---------|---------|
| **M01** | 文档元信息 | 标题、版本、状态、作者、**术语定义**、修订记录 | 术语定义覆盖全文核心业务概念；修订记录含日期+变更人+变更内容 |
| **M02** | 需求背景与目标 | Why(痛点/机会) + 可量化目标 + 成功指标 + **用户角色概览** + **改动差距**(C类场景展开) | 目标可量化、成功指标有具体数值；用户角色含定义+职责；差距逐条追溯到业务场景 |
| **M03a** | 验收策略声明 | 验收方法论 + 总体验收维度（仅方向，不含具体E2E场景） | 验收方向明确；具体E2E场景在M03b中详细定义 |
| **M03b** | 验收标准详细 | Given-When-Then 格式，功能级AC | 每条AC含Given+When+Then；可测试、无模糊词 |
| **M05** | 范围定义 | In Scope(本次做什么) + **Out of Scope**(明确不做什么) | Out of Scope 至少1条；防止范围蔓延 |
| **M06** | 功能清单 | 功能列表 + Kano优先级(基本型/期望型/兴奋型) + 改动类型标注 | 每个功能标注[新增]/[修改]/[复用]；优先级不全是P0 |
| **M07** | 业务流程 | Mermaid全流程图 + 节点说明表 + 状态机(有状态实体) | 每条主流程有起点→终点；节点说明含业务规则；与M03b E2E一一对应 |
| **M08** | 数据模型 | 实体关系 + 字段定义 + 状态枚举 | 核心实体字段完整；状态枚举含触发条件和可流转到 |
| **M09** | 功能详细说明 | 每个功能页：列表/按钮/表单/业务规则 + 改动类型标注 | 聚焦业务规则和数据流转；引用M08数据模型定义 |
| **M10** | 关联与影响 | 系统依赖 + 联动改动 + 改动类型 | 每个关联模块标注改动类型和联动方式 |
| **M11** | 异常与边界 | 数据异常 + 操作异常 + 权限异常 + 环境异常 + 防错机制 | 四维度各至少1条；每条含：触发条件→系统行为→提示文案→恢复方式 |
| **M12** | 权限与敏感信息 | 功能权限矩阵(角色×功能×操作) + 敏感信息处理 | 角色×功能×操作全覆盖；涉敏时五列表格，不涉及时标注"不涉及" |
| **M13** | 非功能需求 | 性能/安全/兼容/可用性/**数据迁移**(涉及已有系统时) | 非功能有具体指标值；数据迁移含迁移规则+回滚策略 |
| **M14** | 编码映射 | 功能树 + 菜单树 | 需 `encoding-source` 配置 |
| **M15** | 版本规划 | 分期计划 + 里程碑 + 各期范围 | 各期范围明确、时间节点具体 |
| **M16** | 开放问题与风险 | 待确认项 + 风险 + 假设前提 | 待确认项有责任人+预期确认时间；风险有影响+缓解措施 |
| **M17** | 运营需求 | 埋点/监控/运营策略 | 埋点有事件名+上报字段；监控有指标+阈值 |
| **M19** | 业务全景定位 | 本需求在业务版图中的位置 + 涉及业务域 + 域间关系 + 功能架构图(Mermaid) | 功能架构图层级清晰；域间关系含交互方式 |

> M03 拆为概览(a)和详细(b)两部分，共 17 个独立模块（M01, M02, M03, M05-M17, M19），18 个标识行（M03 计为 M03a+M03b）。跳号说明：M04(用户角色)和 M18(��动差距)已合并入 M02。

### 模块边界声明

以下模块对容易混淆，明确各自职责：

| 模块对 | 边界 | M02 vs M05 |
|---|---|---|
| **M02 vs M05** | M02 回答"达到什么效果"（业务价值目标），M05 回答"做哪些、不做哪些"（功能边界） | M02 是 Why 的程度，M05 是 What 的边界 |
| **M06 vs M09** | M06 的"说明"列限一句话概述（≤20字），M09 承载全部业务规则细节 | M06 是功能目录，M09 是功能说明书 |
| **M10 vs M19** | M19 回答"我在业务版图的什么位置"（宏观定位），M10 回答"本次改动影响哪些系统"（微观联动） | M19 是地图，M10 是影响清单 |
| **M11 vs M07** | M07 只画异常分支的流程走向（Mermaid 图中的路径），M11 定义异常的完整四维度详情 | M07 是流程图里的异常箭头，M11 是异常处理规范 |
| **M02(角色) vs M12** | M02 含角色概览（定义+职责），M12 含完整权限矩阵（角色×功能×操作） | M02 定义"谁"，M12 定义"谁能做什么" |

### 场景→模块映射

**核心不变量**：所有场景必有 M01 + M02 + M03a。

| M03a 验收标准概览 | ✅ | ✅ | ✅ | ✅ |
| M19 业务全景定位 | ✅ | ○ | - | - |

## PRD 编写硬性规则（10条）

1. **禁止英文表名/字段名**：PRD是业务语言，英文表名让开发跳过业务理解直接看数据库
2. **禁止问号**：待确认项确认后必须转为陈述性结论
3. **禁止模糊描述**：每个指标必须有具体数值，"安全""性能"没有指标值视为违规
4. **异常优先**：先写异常再写正常流程
5. **前后一致**：同一字段全文统一命名
6. **可测试**：每个功能点有对应验收标准，E2E与流程图一一对应
7. **编码映射必填**：涉及菜单/功能改动时生成编码树（需 `encoding-source` 配置）
8. **全面表格化**：正文禁止大段纯文本，Mermaid图和过渡句除外
9. **敏感信息必审**：涉敏必须处理，不涉及也要标注"不涉及"
10. **信息架构先行**：写功能说明前先定义数据实体（详见方法论第1条）

# 适配层

以下内容定义项目结构、模板与质检策略，所有类型共享。

> **注意**：以下项目结构为参考示例。实际路径由 `prd` 命令运行时根据目标仓库目录结构自动探测（详见 `commands/prd.md` Step 1 项目结构探测）。不同项目可能有不同的目录命名（如 `产品项目/编写中/` vs `需求/active/`），prd 命令会自动适配。

## 项目结构约定（参考）

```
项目根目录/
├── 规范/                  # 规范体系
├── 工作管理/              # 任务与计划
├── {业务知识库}/          # 业务知识（名称不固定，含"知识库"即可）
├── {活跃项目目录}/        # 产品功能项目（如：产品项目/编写中/ 或 需求/active/）
└── 运营宣发/              # 功能上线宣发内容（可选）
```

## 模板与自定义覆盖

prd 命令在 `$SPEC_DIR`（规范根目录）下按关键字探测自定义资源文件。没有匹配文件则用内置默认。

| 探测目标 | 有时 | 没有时 |
|------|------|--------|
| PRD 模板文件（如 `规范/模板/PRD/标准PRD模板.md`） | 按用户模板生成（只生成模板中列出的章节） | 按场景→模块映射动态选配 |
| 质检/缺失项检查文件 | 按用户清单自检 | 按激活模块逐一检查 |
| 格式模板文件 | 按用户格式模板 | 见 `references/prd-format-templates.md` |
| 评审标准文件（如 `规范/评审标准/`） | 用用户评审标准 | 按默认评审参数执行 |
| 运营宣发模板 | 按用户模板生成 | 按默认宣发参数生成 |
| 敏感信息策略文件 | 按用户策略处理 | 按内置规则识别（手机号/邮箱/身份证号） |

涉及界面改动时，UI 原型目录由 prd 命令探测决定（沿用已有项目惯例，默认 `07-prototype/`）。

## 编码映射

涉及菜单/功能编码改动时，在项目 `CLAUDE.md` 中声明 `prd.encoding-source` 指定编码数据源路径（数据引用，不是模板）。配置后生成 `10-function-tree.md` + `11-menu-tree.md`。
