# 技术组件选型

## 产物路径

| 产物 | 输出路径 | 说明 |
|------|---------|------|
| 技术组件选型结果 | `$WORK_DIR/design/tech-design.md` 第 8.2 节 | 选定方案、实现方式、选择理由 |

工作目录：`$WORK_DIR` = `$JLC_AI_WORKSPACE/process-docs/{需求编号}`。

## 核心原则

**技术组件的选型不允许由 AI 自行决定，必须通过 brainstorming 候选枚举 + 用户确认流程。**

原因：同一个 UI 模式往往有多种实现方式（组件库原生组件 vs 项目封装组件 vs 自定义开发），AI 难以准确判断项目约定和团队偏好。brainstorming 模式将"选择权"交给用户，AI 只负责"枚举、分析、推荐"。

## 触发条件

当需求涉及以下前端页面/交互时，**必须**执行技术组件选型 Brainstorming：
- 原型/UI设计稿中存在**非标准 UI 模式**（非简单增删改查，如自定义卡片、倒计时按钮、特殊图表等）
- 原型中存在**多种相似但有差异的 UI 交互**（如：同一页面有多种表格形态）
- 原型中的 UI 模式在项目中有**多种已有实现**可供参考
- 原型中涉及**复杂交互组件**（可编辑表格、级联选择、动态表单等）

以下场景**不需要**组件选型 Brainstorming：
- 纯后端需求，无前端页面
- 简单的列表展示 + 表单弹窗（项目已有统一模式）
- 原型 UI 模式与项目中已有实现完全一致，无选型分歧

**跳过记录要求：** 当判断某选型项无需 Brainstorming 时，必须在对话上下文中记录跳过原因（如"列表展示：项目已有 SuperTable 统一模式，无选型分歧"）。禁止静默跳过。

## 选型维度

对每个需要选型的 UI 模式，从以下维度对比候选方案：

| 维度 | 说明 |
|------|------|
| 实现方式 | 具体使用哪个组件、什么 API、什么配置 |
| 开发成本 | 预估工作量（低/中/高） |
| 可维护性 | 代码复杂度、后续修改难度 |
| 性能影响 | 大数据量场景下的表现 |
| 项目先例 | 项目中是否已有相同模式的使用案例 |
| 一致性 | 与项目其他页面的风格是否统一 |

## Brainstorming 流程

### Step 1: 原型分析 + 项目代码扫描（AI 执行）

1. **逐页分析原型**：遍历原型/UI设计稿的每个页面，识别所有需要技术选型的 UI 模式
2. **分类归纳**：将相似 UI 模式归为一组，避免重复选型
3. **扫描项目代码**：
   - 在前端项目代码中搜索相似 UI 模式的已有实现
   - 定位关键组件文件和封装模式
   - 记录已有的组件封装（如项目是否有 `ProTable`、`SearchForm` 等封装）

### Step 2: 候选方案枚举（AI 执行，不筛选）

对每个选型项，提出 **3 个及以上候选方案**。**禁止在枚举阶段只提一个方案**，必须提供可对比的选项。如果确实难以提出 3 个独立方案，至少提供 2 个，并在描述中说明为何只有 2 个选项。

枚举规则：
- 每个方案必须具体到可执行的实现方式（组件名、API 调用方式、关键配置项）
- 标注方案在项目中的已有先例（哪个页面用了类似实现）
- 如果某个方案是项目推荐模式，优先列出并标注

典型对比维度示例：

| UI 模式 | 典型方案对比 |
|---------|------------|
| 数据表格 | A. 项目封装 ProTable（自带搜索+分页） vs B. 原生 Table + 手动分页 |
| 表单弹窗 | A. 项目封装 ModalForm vs B. 自定义 Dialog + Form |
| 级联选择 | A. Cascader 组件 vs B. 多级 Select 联动 |
| 可编辑表格 | A. 行内编辑模式 vs B. 弹窗编辑模式 vs C. 混合模式 |
| 复杂表单 | A. 分步表单（Steps） vs B. Tab 切换 vs C. 折叠面板 |

### Step 3: 呈现候选方案供用户确认

以结构化格式呈现，**禁止自行决定最终选取**，必须等用户确认：

```
## 技术组件选型候选方案

### 选型项 1：{原型页面名称} - {UI模式描述}

> 原型截图参考：{描述原型中该模式的视觉特征}

| # | 方案 | 实现方式 | 优点 | 缺点 | 项目先例 |
|---|------|---------|------|------|---------|
| A | {方案名} | {具体实现} | {...} | {...} | {页面X已使用} |
| B | {方案名} | {具体实现} | {...} | {...} | {无/有} |

**推荐：** A — 理由：{具体原因}

请确认选择哪个方案（回复编号，如 "A" 或 "A+B混合"）：
```

### Step 4: 用户确认后锁定

- 用户确认后，将选定方案记录为最终技术组件选型
- 后续技术方案**严格使用用户确认的方案**，不得自行更换
- 选型结果写入 `tech-design.md` 前端架构章节的"技术组件选型"小节

## 常见错误警示

| 错误模式 | 示例 | brainstorming 如何避免 |
|---------|------|----------------------|
| 只提一个方案 | "这个表格用 ProTable" | 必须提供 2-3 个可对比方案 |
| 方案描述太抽象 | "用组件库" vs "自己写" | 方案必须具体到组件名和 API |
| 忽略项目约定 | 推荐了项目不使用的第三方库 | 优先分析项目已有实现模式 |
| 遗漏复杂交互 | 只看到表格，忽略了可编辑行 | 逐页分析原型，系统识别所有模式 |
| 不考虑数据量 | 大数据量场景推荐了虚拟滚动缺失的方案 | 候选方案中标注性能影响 |

## 自检验证

**覆盖度检查：**
- [ ] 原型中每个页面的非标准 UI 模式都已识别并纳入选型
- [ ] 每个选型项都有 3 个及以上可对比的候选方案（或 2 个并附理由）
- [ ] 每个方案都标注了项目先例（已有使用/无先例）
- [ ] 跳过 Brainstorming 的选型项均有书面跳过理由记录

**一致性检查：**
- [ ] 用户确认的选型结果与写入 tech-design.md 第 8 章的内容一致
- [ ] 选型结果与前端组件结构设计（第 8.3 节）无矛盾
- [ ] 所有选型项来自原型分析，无凭空设计的组件

**质量检查：**
- [ ] 方案描述具体到组件名和 API 调用方式，非抽象描述
- [ ] 推荐方案附有明确理由
- [ ] 高数据量场景已评估性能影响
